# NetPulse 완성 루프 기획서

- 작성일: 2026-11-13
- 상태: 5차안 (방향 전환: 처음부터 새로 만들기 + 글래스 디자인. Codex 3차 검토 반영, 5차안 자체는 재검토 전)
- 대상 저장소: `Ow-wL/NetPulse` (`main`, 커밋 2개, 공개 저장소)

이 문서는 Claude Code와 Codex가 함께 NetPulse를 완성까지 끌고 가는 루프의 단일 기준 문서다.
루프의 모든 회차는 이 문서와 `docs/loop/STATE.md`를 먼저 읽고 시작한다.

---

## 1. 목표

NetPulse를 **처음부터 새로 만든다.** 누구나 받아서 바로 쓰는 네트워크 끊김 진단 도구이고, 보는 순간 "잘 만든 제품"으로 느껴지는 화려한 글래스 디자인을 갖춘다.

- 기존 코드와 화면은 **어떤 기능이 있었는지 참고하는 자료**로만 쓴다. 구조, 화면, 파일 형식은 이어받지 않는다.
- 디자인은 기능과 같은 무게의 요구사항이다. 디자인 게이트를 통과하지 못한 마일스톤은 완료가 아니다.

### 완성 정의

**루프 완료** — 아래가 모두 참이면 루프가 끝난다.

1. 6절의 필수 기능 23개(F1~F7, R1~R5, N1~N9, N13, N14)가 모두 동작하고 수용 기준을 통과했다.
2. 7절의 디자인 요구(유리 재질, 다크·라이트 테마, 모션, 접근성 대체)가 모든 화면에 적용됐다.
3. 처음 실행한 사용자가 설정 없이 측정을 시작할 수 있다.
4. 자동 테스트와 CI가 있고, 깨끗한 클론에서 문서화된 한 가지 절차로 배포 파일이 만들어진다.
5. 모든 마일스톤이 검증 게이트 G1~G5를 통과했고, 각 마일스톤의 PR이 올라가 있다.
6. 쌓인 PR의 맨 위 커밋에서 전체 게이트를 다시 통과했다. (M11)

**제품 출시** — 루프가 끝난 뒤 사용자가 하는 일이다.

7. 사용자가 인수 체크리스트(실제 단선 실험, 장시간 측정, 화면 품질)를 확인한다.
8. 사용자가 PR을 머지하고 Release 게시를 승인한다.

## 2. 출발점

### 기존 앱 (기능 참고용)

`main`(`e852c6b`)의 C# / WPF 앱이다. 소스 3,082줄, `Build.ps1`로 빌드된다.

| 기능 | 하는 일 | 참고 위치 |
| --- | --- | --- |
| 빠른 진단 | 어댑터, 게이트웨이, 외부 TCP, DNS, HTTPS, 네트워크 로그인, 최근 링크 이벤트를 점검하고 결론 문장을 제시 | `QuickDiagnostics.cs` |
| 사이트 점검 | 입력한 도메인의 DNS와 HTTPS를 따로 확인 | `QuickDiagnostics.cs:142` |
| 실시간 측정 | 여러 대상에 1초마다 병렬 Ping, 손실·지연·연속 손실 집계, CSV 기록 | `Monitor.cs` |
| 증상 표시 | 사용자가 끊김을 느낀 시각을 기록 | `Evidence.cs:63` |
| 경로 기록 | 대상별 Windows 경로(인터페이스)의 초기값과 변경 기록 | `Evidence.cs:71` |
| 링크 근거 | 시스템 로그에서 유선 링크 다운·업 이벤트 조회 | `Evidence.cs:143` |
| 끊김 분석 | 회차별 응답 조합으로 원인 구간 후보 제시 | `Analysis.cs` |
| 결과 비교 | 두 측정의 손실률과 지연 비교 | `Comparison.cs` |
| 보조 | DNS 캐시 비우기(확인 후), Windows 설정 열기, 결과 폴더 열기 | `QuickWindow.cs` |

M0에서 이 표를 **기능 명세서**(`docs/loop/feature-inventory.md`)로 풀어 쓴다. 각 기능의 입력, 출력, 판정 규칙, 알려진 결함을 적는다. 이후 새 구현은 이 명세서와 6절을 기준으로 하고, 기존 소스를 옮겨 적지 않는다.

### 기존 앱을 버리는 이유

- 대상 IP와 `Mesh`/`WiFi` 모드가 코드 전체에 고정되어 있어 다른 네트워크에서 쓸 수 없다.
- 링크 근거가 Intel 드라이버 하나에 묶여 있고, 그 드라이버가 없으면 근거 없이 "정상"으로 표시한다 (`QuickDiagnostics.cs:358`).
- 색상 58곳이 XAML과 C#에 직접 박혀 있고 라이트 테마 하나뿐이다. 애니메이션은 사실상 없다.
- `Glass`라는 스타일은 거의 불투명한 흰색 그라디언트다. 뒤가 비치거나 흐려지지 않는다.
- 분석·비교·진단이 모두 별도 모달 창이다.
- 자동 테스트가 없다.

## 4. 루프 설계

### 4.1 역할

| 주체 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| Claude Code | 지휘, 설계안 작성, 구현, 검증 실행, 커밋·푸시·PR, 상태 기록 | Codex 답을 지어내거나 요약으로 대체 |
| Codex | 설계안·diff·화면 캡처를 보고 판정과 근거 제시, 대안 제안 | 파일 수정, 패키지 설치, 외부 작업 |
| 사용자 | 중대 결정 컨펌, 최종 인수, 머지, Release 승인 | 매 회차 승인 |

Codex는 반대 의견을 내는 역할이다. Claude는 Codex에게 결론을 유도하지 않고, 검토 대상과 근거만 전달한다.

### 4.2 마일스톤 한 바퀴

```
① 설계안 작성 (Claude)
② 설계 검토 (Codex)            ─┐ 최대 2라운드
③ 합의 또는 판정 (Claude)      ─┘
④ 구현 → 로컬 커밋 (검토 대상 SHA 확정)
⑤ 검증 게이트 G1 → G2 → G3 → G5 자동 검사와 Claude 시각 검토   (그 SHA에서 실행)
⑥ diff 리뷰 G4 (Codex, 화면 캡처 검토 포함) ─┐ 최대 3라운드
   지적 반영 → 새 커밋 → ⑤                  ─┘
   G4가 승인되면 G5도 확정
⑦ 마감: 기록 커밋 → 공개 전 검사 → 푸시 → PR → CI 확인 → 다음 마일스톤
```

1. **설계안 작성**: `docs/loop/M{n}-design.md`에 목표, 만들 파일, 수용 기준, 테스트 계획, 화면이 있으면 화면 구성과 상태·모션 정의, 위험, 대안을 적는다.
2. **설계 검토**: Codex가 설계안을 읽고 `APPROVE` / `REVISE` / `BLOCK`으로 판정한다.
3. **합의**: Claude가 지적마다 수용 또는 반박을 근거와 함께 적는다. 4.4의 규칙으로 판정한다.
4. **구현**: 브랜치에서 작업하고 로컬에 커밋한다. 이 커밋의 SHA가 검토 대상이다.
5. **검증 게이트**: 그 SHA에서 게이트를 순서대로 돌리고, 결과와 SHA를 `STATE.md`에 적는다. 화면이 없는 마일스톤은 G5를 건너뛰고, G3은 **화면 없는 통합 시나리오**로 대신한다 (4.3). M0은 8절의 전용 절차를 따른다.
6. **diff 리뷰**: Codex가 `git diff {base SHA}..{검토 SHA}`와 변경 파일 목록, 게이트 결과, 화면 캡처를 보고 판정한다.
7. **마감**: 4.8의 순서로 진행하고 바로 다음 마일스톤으로 넘어간다.

**검토한 것과 내보내는 것을 일치시키는 규칙**

- 작업트리가 깨끗한 상태에서만 게이트와 리뷰를 시작한다.
- G4 `APPROVE` 이후 코드가 한 줄이라도 바뀌면 게이트를 전부 다시 돈다.
- 예외는 `docs/loop/` 아래 기록 파일만 바꾼 커밋이다. 이 커밋은 게이트를 무효화하지 않는다.
- 푸시하는 브랜치의 코드 커밋은 `APPROVE`를 받은 SHA와 같아야 한다. PR 본문에 그 SHA를 적는다.

### 4.3 검증 게이트

| 게이트 | 통과 조건 | 방법 |
| --- | --- | --- |
| G1 빌드 | 종료 코드 0, 경고가 늘지 않음 | D1에서 확정한 빌드 절차 |
| G2 로직 테스트 | 전부 통과. 새 로직에는 테스트가 함께 추가됨 | 테스트 러너 |
| G3 기능 시나리오 | 실제 앱에서 시나리오의 기대값이 모두 맞음 | UI 자동화로 조작하고 화면의 값과 저장 파일을 검사 |
| G4 Codex 리뷰 | 검토 SHA에 대한 `APPROVE` | `codex exec` (4.6) |
| G5 디자인 | 자동 검사 통과 + 캡처 매트릭스 시각 검토 통과 | 7.8절 |

**G3 기능 시나리오**는 "화면이 떴다"가 아니라 "기대한 값이 나왔다"를 검사한다.

- G1이 방금 만든 바로 그 실행 파일을 띄운다.
- 조작 전후로 상태를 기다린다. 로딩이 끝나고 기대한 값이 나타날 때까지, 단계별 제한시간 안에서 대기한다.
- 기대값을 검사한다. 예: 분석 화면이 픽스처의 측정 ID, 회차 수, 끊김 횟수, 등급, 원인 후보 문구를 표시하는지.
- 끝에서 끝까지 잇는다: 시작 → 짧은 측정 → 증상 표시 → 중지 → 기록에서 다시 열기 → 리포트 내보내기. 화면이 생기는 마일스톤마다 시나리오가 길어진다.
- 예기치 않은 오류 화면이나 대화상자가 뜨면 실패다.
- **조작 허용 목록**을 둔다. DNS 캐시 비우기, Windows 설정 열기처럼 시스템 상태를 바꾸거나 다른 프로그램을 띄우는 컨트롤은 누르지 않는다.

UI 자동화 수단은 스택에 따라 다르므로 D1에서 함께 정한다. 웹 기술 화면이면 브라우저 자동화, 네이티브 화면이면 UI Automation이다.

**데모 모드**를 M1에서 만든다. 합성 데이터로 앱 전체를 돌리는 실행 옵션이다.

- G3과 G5의 캡처는 데모 모드에서 찍는다. 이 PC의 실제 IP나 어댑터 이름이 캡처에 들어가지 않으므로 Codex에 보여주고 PR과 README에 실을 수 있다.
- 끊김, 지연 급증, 근거 수집 실패 같은 상황을 시나리오로 재생한다. 실제로 재현할 수 없는 상태의 화면을 이것으로 검증한다.
- **데모는 가장 바깥에서만 바꿔 끼운다.** 합성 데이터는 측정과 근거 수집의 입력 자리에 들어가고, 집계·저장·분석·화면은 제품 코드를 그대로 탄다. 완성된 화면용 데이터를 직접 넣지 않는다. 그래야 데모가 통과하면 그 뒤 경로도 검증된 것이다.

**데모만으로 통과시키지 않는 것**

- **화면 없는 통합 시나리오**: 엔진 마일스톤(M3, M4)은 실제 Windows의 측정·근거 수집과 실제 저장소를 연결해 짧은 측정 → 중지 → 저장 → 다시 읽기를 통과해야 한다. G3을 대신한다.
- **실측 시나리오**: 화면 마일스톤마다 데모 옵션 없이 짧은 측정 → 중지 → 저장 → 다시 열기를 한 번 돌린다. 이 캡처와 로그는 4.7의 공개 기록 규칙에 따라 공개하지 않는다.
- **판정을 둘로 나눈다**: 응답이 성공했는가는 그때의 네트워크에 달렸으므로 통과 조건이 아니다. 앱이 관측한 것을 정확히 기록하고 보여주는가가 통과 조건이다.
- M11에서 최종 배포 파일을 데모 옵션 없이 실행해 같은 시나리오를 확인한다.

**미리 인정하는 한계**

- 실제 끊김은 자동으로 재현할 수 없다. 분석과 알림은 합성 데이터로 검증한다.
- 다른 제조사 어댑터 PC가 없다. 픽스처 테스트는 해석 로직만 검증한다.
- 실제 단선 실험과 실제 시간의 장시간 측정은 사용자 인수 항목이다. **실시하지 않은 것을 통과로 적지 않는다.**
- 화면은 이 PC의 한 가지 해상도에서 확인하고, 배율은 100%와 150%를 확인한다.

### 4.4 의견 충돌 판정 규칙

설계 단계의 이견과 구현 승인을 분리한다.

**설계 이견 (②③ 단계)**

1. 근거 우선: 파일, 로그, 테스트 결과가 추론보다 우선한다.
2. 실험 가능하면 실험: 차이를 가릴 테스트나 스파이크가 있으면 돌려서 결과로 정한다.
3. 2라운드 후에도 불일치하면
   - 중대 결정(4.5)은 두 의견과 근거를 나란히 사용자에게 제시하고 멈춘다.
   - 그 외에는 Claude가 결정하고, Codex의 반대 의견을 `DECISIONS.md`에 그대로 남긴다. 이 쟁점은 diff 리뷰에서 다시 검토받는다.

**디자인 이견**: 두 종류로 나눈다.

- **결함**: 대비 미달, 프레임 기준 미달, 접근성 대체 누락, 사용자가 고른 시안(D2)이나 7절 원칙의 위반. 고쳐야 통과한다.
- **취향 차이**: 기준 안에서의 선호. Claude가 D2에 더 가까운 쪽으로 정해 진행하고, 두 안과 Codex의 의견을 `DECISIONS.md`에 남긴다. 루프를 멈추지 않고, 4.5의 멈추지 않는 보고에 함께 실어 사용자가 볼 수 있게 한다.

**구현 승인 (⑥ 단계)**

- 푸시하려면 검토 SHA에 대한 G4 `APPROVE`가 반드시 있어야 한다. Claude가 대신 판정하지 않는다.
- 루프는 승인받지 못한 변경을 푸시하지 않는다. 승인을 못 받으면 멈추고 보고한다. 사용자가 따로 지시한 수동 푸시는 루프 밖의 일이고, 게이트 통과나 마일스톤 완료로 세지 않는다.
- 시간 초과, 부분 답변, 판정 누락은 승인이 아니다.
- 높음·중간 심각도 지적은 고치거나, Codex가 다음 라운드에서 철회해야 한다. 낮음 지적은 `APPROVE`와 함께 남을 수 있고 PR에 적는다.
- 두 모델이 같은 의견이어도 정답으로 단정하지 않는다. 나머지 게이트가 함께 통과해야 한다.

### 4.5 사용자 컨펌이 필요한 중대 결정

- **D1 기술 스택**과 주요 의존성 목록 (5절)
- **D2 디자인 방향** (7.7절)
- 필수 기능의 추가·삭제, 마일스톤 순서 변경
- D1에서 승인한 목록 밖의 제품 런타임 의존성 추가
- 이 PC에 개발 도구를 새로 설치하는 일
- 관리자 권한 요구, 사용자 네트워크 설정을 바꾸는 기능 추가
- GitHub Release 게시, `main` 머지

이 목록 밖의 일은 묻지 않고 진행한다. D1과 D2는 M0에서 **한 번에** 묻는다.

**멈추지 않는 보고**: 화면이 생기는 마일스톤이 끝날 때마다 데모 모드 캡처를 사용자에게 보낸다. 답을 기다리지 않고 다음으로 넘어간다.

- 답이 없으면 추가 승인이 아니라 기존 D2를 유지하는 것으로 본다.
- 사용자가 의견을 주면 `DECISIONS.md`에 적는다: 이미 끝난 마일스톤을 고쳐야 하는지, 영향 범위, 다시 돌릴 게이트. 디자인 시스템을 바꾸는 의견이면 그 수정을 다음 마일스톤보다 먼저 한다.

### 4.6 Codex 호출 규약

전역 규칙(`~/.claude/CLAUDE.md`)을 그대로 따른다.

**읽기 전용 강제**

- 호출: 저장소 루트에서 `codex exec --skip-git-repo-check --sandbox read-only`. 자동 승인이나 권한 확대 옵션은 쓰지 않는다.
- 요청문에도 "파일 수정·설치·외부 작업 금지"를 적는다. 이것은 보조 방어다.
- 호출 전후로 `git status --short`와 HEAD를 비교한다. 달라졌으면 그 호출을 무효로 하고 멈춘다.
- M0의 첫 호출에서 샌드박스가 쓰기를 실제로 막는지 확인한다. (이 기획서 검토 호출 세 번에서는 전후 작업트리가 같았다.)

**요청 내용**

- 긴 요청은 파일로 써서 표준 입력으로 넘긴다.
- 담는 것: 검토 대상 경로, base·검토 SHA, 변경 파일 목록, 요구사항과 제약, 판단 기준, Claude의 결론과 근거, 게이트 결과.
- 화면 검토에는 데모 모드 캡처를 이미지로 첨부한다. 실제 네트워크 정보가 찍힌 캡처는 첨부하지 않는다.
- 끝에 붙이는 것: "실제로 확인한 것과 추정을 구분해줘. 못 읽었으면 추측하지 말고 못 읽었다고 말해줘."
- 파일은 UTF‑8로 읽게 한다. PowerShell 출력이 깨지면 다른 UTF‑8 읽기 수단을 쓰라고 적는다.

**실패 처리**

- 대기 한도 10분. 초과하면 Codex 프로세스가 끝났는지 확인하고, 남아 있으면 종료한 뒤 1회 재시도한다.
- 부분 출력은 판정으로 쓰지 않는다. 원문은 보관하되 "미완료"로 표시한다.
- 재시도도 실패하면 "교차 검토 미완료"로 기록한다.
  - 설계 검토였다면 구현은 진행할 수 있다. 미검토 설계는 diff 리뷰 요청에 함께 넣는다.
  - diff 리뷰였다면 푸시하지 않고 멈춰서 사용자에게 알린다.

**기록**: Codex 답변 원문은 `.loop/reviews/`에 저장한다.

판정 요청 형식:

```
판정: APPROVE | REVISE | BLOCK
지적: [심각도 높음/중간/낮음] 파일:줄 — 문제 — 근거 — 제안
확인한 자료: ...
확인하지 못한 부분: ...
```

### 4.8 git과 PR

**브랜치 체인**

- `loop/m0-decisions`의 base는 `main`이다.
- 이후 마일스톤 브랜치는 직전 마일스톤 브랜치에서 갈라지고, PR의 base도 직전 브랜치다.
- 머지는 사용자가 한다. 루프는 머지를 기다리지 않고 다음 마일스톤으로 넘어간다.

**기존 소스의 처리**

- M1에서 기존 소스를 `legacy/`로 옮긴다. 새 코드와 섞이지 않게 하고, 루프 동안 기능 참고용으로 읽는다.
- M10에서 `legacy/`를 지운다. 이후에는 git 이력에서만 볼 수 있다.

**마감 순서**

1. 게이트 통과를 확인한다.
2. `STATE.md`, `DECISIONS.md`를 갱신해 기록 전용 커밋을 만든다.
3. **공개 전 검사**: 새로 원격에 올라갈 커밋 하나하나의 내용과 PR 본문을 4.7의 금지 항목 패턴으로 검색한다.
4. 푸시하고 PR을 만든다.
5. **CI 확인**: 그 PR head의 CI 결과를 확인한다. 통과해야 마일스톤 완료다.

**검사나 CI에서 걸렸을 때**

- 공개 전 검사에 걸린 커밋은 아직 푸시 전이므로 로컬에서 고쳐 쓴다.
  - 기록 파일만 고쳤으면 공개 전 검사부터 다시 한다.
  - 코드 커밋이 바뀌었으면 새 검토 SHA로 게이트에 돌아간다.
- CI가 실패하면 고친 뒤 새 검토 SHA로 게이트를 다시 통과하고 추가 커밋으로 푸시한다.
- 어느 경우든 4.9의 라운드와 실패 횟수는 이어서 센다.

**PR 본문**: 변경 요약, 승인받은 SHA, 게이트 결과, Codex 판정 요약, 데모 모드 캡처, 남은 낮음 지적, 미검증 범위.

강제 푸시, `main` 직접 커밋, 훅 우회는 하지 않는다.

### 4.9 멈춤 조건과 상한

루프는 아래 경우에만 멈춘다.

- 루프 완료 조건(1절의 1~6)을 모두 충족했다.
- 4.5의 중대 결정이 필요하다.

## 5. 결정 게이트 D1: 기술 스택

새로 만들기로 했으므로 기존 스택에 묶이지 않는다. 고르는 기준은 세 가지다.

1. **유리 재질과 모션의 표현력** — 특히 창 안쪽에서 패널 뒤 콘텐츠를 실시간으로 흐리게 할 수 있는가.
2. **진단 기능의 구현 난이도** — 비관리자 ICMP, 이벤트 로그, Win32 호출.
3. **배포** — 설치 없이 받아서 실행.

**"설치 없이"의 뜻** (10절에서 함께 확인받는다)

- 지원 대상은 Windows 11이다.
- 설치 프로그램 없이, 받은 파일을 실행하거나 압축을 풀어 실행한다. 파일 하나인지 폴더인지는 조건이 아니다.
- Windows 11에 기본으로 들어 있는 런타임(WebView2, .NET Framework)을 쓰는 것은 허용한다. 없거나 너무 낮은 버전이면 앱이 알아보고 안내한다.
- 그 밖의 런타임을 사용자가 따로 설치해야 하는 구성은 허용하지 않는다. 필요하면 배포 파일에 포함한다.

- Flutter: 조사한 유리 패키지가 Windows를 지원하지 않고, 진단 기능을 외부 호출로 붙여야 한다.
- WPF (.NET Framework 4.8): D와 같은 한계에 구식 언어까지 겹친다.

### 현재 의견 (스파이크 전이므로 잠정이다)

- Claude: **A를 1순위, C를 2순위**로 본다. 요구의 중심인 유리와 모션은 웹 기술이 가장 강하고, 진단 기능은 .NET이 가장 쉽다. A는 이 PC에 필요한 도구가 이미 다 있다.
- Codex: 같은 순위다. 화면은 웹, 측정·저장·판정·알림은 .NET에 두는 역할 분담이 맞다고 봤다. A의 진짜 위험은 통신 코드량이 아니라 수명주기와 신뢰 경계라고 지적했다.
- 두 의견이 같지만 **둘 다 만들어 보지 않았다.** 스파이크 결과로 정한다.

### M0 스파이크

A와 C로 같은 시험 화면을 만든다. **움직이는 실시간 그래프 위에 유리 패널이 떠 있고, 다크·라이트 전환과 화면 전환 애니메이션이 있는 화면**이다. 재는 것:

| 영역 | 재는 것 |
| --- | --- |
| 유리와 모션 | 유리 효과가 실제로 나오는지 캡처로 비교. 패널을 겹쳤을 때, 테마를 반복 전환할 때 |
| 성능 | 평균 프레임 수만이 아니라 프레임 시간 분포, 멈춤, 입력 지연. 프로세스 전체의 CPU·GPU·메모리 |

| 배포 | 파일 크기, 첫 실행 시간, 쓰기 제한 위치에서 시작, 풀리는 위치와 크기, 런타임 전제 |
| 자동화 | 명령줄 빌드와 UI 자동화가 최종 실행 파일에 연결되는지. 창 전체 캡처와 화면 내부 캡처의 차이 |

**합격선을 먼저 정한다.** 스파이크를 돌리기 전에 항목별 최소 기준을 `DECISIONS.md`에 적는다. 재본 뒤에 유리한 기준을 고르면 비교의 의미가 없다.

결과와 캡처를 두 모델의 의견과 함께 사용자에게 제시한다. B는 A가 성립하지 않을 때만 다시 검토한다. Rust 설치가 필요하기 때문이다.

**D1 컨펌에 함께 올릴 것**: 주요 의존성 목록(UI 프레임워크, 차트, 테스트 도구), 최소 지원 Windows 버전.

**R1의 구간 판단 원칙**

사용자가 정한 대상 순서는 실제 패킷 경로를 증명하지 않는다.

- 응답 조합은 관측 결과로 표시하고, 원인 구간은 후보로 제시한다.
- 가까운 대상은 실패하고 먼 대상은 성공하면 구간을 단정하지 않는다.
- 한 번도 응답한 적이 없는 대상은 "응답 기준선 없음"으로 구별한다. Ping을 막는 장비일 수도 있고, 이미 끊긴 상태에서 측정을 시작한 것일 수도 있다. 다른 대상이 응답하면 앞의 경우로 보고 구간 판단에서 빼고, 모든 대상이 처음부터 무응답이면 "끊긴 상태에서 시작했을 수 있음"으로 알린다.
- 대상별 Windows 경로가 프로필의 예상 연결 유형과 다르면 판단을 보류한다.

**끊김 판정의 구분**

"끊김"을 한 가지로 뭉뚱그리지 않는다. 판정은 넷 중 하나다.

| 판정 | 뜻 |
| --- | --- |
| 대상 응답 실패 | 특정 대상 하나가 응답하지 않음. 그 대상의 문제일 수 있음 |
| 외부 연결 단절 추정 | 서로 독립된 외부 대상들이 함께 실패. 공유기가 응답하더라도 해당 |
| 로컬 링크 단절 관측 | 어댑터의 링크가 내려간 것을 직접 관측 |
| 판단 불가 | 유효한 관측이 부족하거나 근거가 엇갈림 |

- 외부 대상은 서로 다른 사업자의 주소로 둘 이상 둔다. 한 곳의 장애를 인터넷 단절로 오해하지 않기 위해서다.
- 대상마다 역할(로컬 장비, 외부)을 기록한다. 판정에 필요한 최소 유효 대상 수와 임계값은 M4 설계에서 정한다.

**R2의 근거 상태**

- 링크 근거에 어느 어댑터의 것인지 기록하고, 측정에 쓰인 인터페이스와 연결한다.
- 상태를 네 가지로 구별한다: 수집 미지원 / 접근 거부 / 관측했으나 이벤트 없음 / 끊김 관측. **앞의 둘을 "정상"으로 표시하지 않는다.**
- 기본 경로는 측정 중 인터페이스 상태의 직접 관측이고, 이벤트 로그는 보완 경로다. 수집 방식은 M4 설계에서 이 PC의 실측으로 정한다.
- "모든 드라이버의 모든 순간을 잡는다"는 약속이 아니다. 지원 환경, 관측 해상도, 미지원 시 표시를 문서로 정한다.

### 필수 기능의 최소 범위

필수 23개는 개수보다 깊이가 문제다. 깊이가 열려 있는 항목은 최소 범위를 여기서 못 박는다. 이보다 더 만드는 것은 각 마일스톤 설계에서 정한다.

| 기능 | 최소 범위 |
| --- | --- |
| N1 겹침 타임라인 | 한 측정 안에서 확대와 좌우 이동. 손실, 증상 표시, 링크 이벤트 마커 |
| N2 등급 | 등급 단계에 "관측 부족"과 "판단 불가"를 포함. 근거 없이 좋은 등급을 주지 않음 |
| N6 리포트 | 외부 파일 없이 열리는 파일 형식 한 가지 |
| N7 트레이와 알림 | 창 닫기와 앱 종료를 구분. 다시 열기. 같은 끊김에 알림을 반복하지 않음 |
| N8 메모 | F4 증상 표시에 글을 붙이는 것까지 |
| R5 | 6.2의 여섯 항목 |

**측정 시간과 종료 동작**

- 측정 시간의 기본값과 최대값은 기존 앱의 값(10분, 720분)에서 출발하고 M3 설계에서 확정한다.
- N7(필수)은 정해진 시간의 측정을 트레이에서 계속하는 것이다. N12(선택)는 시간 제한이 없는 측정과 오래된 기록의 정리다.
- 측정 중 창을 닫으면 트레이로 숨고 측정은 계속된다. 처음 한 번 안내한다. 트레이의 "종료"를 누르면 기록을 저장한 뒤 끝난다.

### 기존 앱에서 반드시 이어받을 판단 규칙

코드는 옮기지 않지만, 아래 규칙은 기존 앱이 옳게 하던 것이다. M0의 기능 명세서에 적고 새 엔진의 테스트로 만든다.

- 검사 오류는 손실과 구별하고 손실률의 분모에서 뺀다. 평균 지연은 성공한 응답만으로 구한다. 유효한 관측이 없으면 0이 아니라 "값 없음"이다.
- 누락된 회차를 건너 연속 손실을 잇지 않는다. 관측 공백을 정상으로 그리지 않는다.
- 대상이 빠졌거나 검사 오류가 있는 회차는 불완전 관측이다.
- 게이트웨이가 Ping에 응답하지 않는다고 바로 장애로 단정하지 않는다.
- HTTPS는 되는데 IPv4 직접 연결이 실패하면 IPv6, 프록시, VPN 가능성을 설명한다.
- 여러 검사 중 일부만 성공한 것을 전체 실패와 구별한다.
- 측정의 종료 사유(완료, 중지, 오류)와 저장 실패를 구별한다.

반대로 이어받지 않는 것: 고정된 대상과 모드, 모든 대상에 같은 지연 기준, 특정 드라이버 의존, "이벤트 없음 = 정상", 손실의 첫 표본과 마지막 표본의 시각 차이를 실제 끊김 길이처럼 보이게 하는 표현.

기능 명세서에는 기존 앱의 세부 동작도 빠짐없이 적고, 새 앱에서 유지할지 뺄지를 하나씩 정한다. 예: 결과를 클립보드로 복사, 빠른 진단을 다시 돌렸을 때 이전 결과와 비교, 다른 위치의 측정 파일 열기, 이상 구간 앞뒤 회차와 당시 경로 표시.

### 넣지 않는 것

| 기능 | 이유 |
| --- | --- |
| 앱별 트래픽 감시, 방화벽 | 관리자 권한이나 드라이버가 필요하고 끊김 진단과 목적이 다르다 |
| 기기 스캔, 침입자 탐지 | 범위 밖이고 보안 제품으로 오해받는다 |
| Wi‑Fi 히트맵 | 전문가용이고 작업량이 크다 |
| 속도 측정 | 측정 서버가 필요하고, 끊김과 대역폭은 다른 문제다 |
| 계정, 클라우드, 이메일 알림 | 서버 없는 단독 실행 원칙에 어긋난다 |
| IPv6 측정, 문제 자동 수리, 다국어 UI, 설치 프로그램, 자동 업데이트, 코드 서명 | 이번 범위 밖 |
| 기존 앱이 만든 측정 결과 열기 | 새로 만드는 앱이고 형식을 이어받지 않는다 |

### 수용 기준의 원칙

기능별 수용 기준은 각 마일스톤 설계안에서 확정하고 Codex 검토를 받는다. 모든 기능에 공통인 기준은 다음과 같다.

- 판정 로직(끊김, 구간 후보, 등급)은 합성 데이터 테스트로 검증한다. 경계 사례를 포함한다: 가까운 쪽 실패·먼 쪽 성공, 항상 무응답인 대상, 측정 오류, 누락 회차, 경로 불일치.
- 설정과 기록은 손상, 저장 실패, 재시작 후 복원을 테스트한다.
- 리포트는 가리기를 켠 결과에 원본 식별 정보가 남지 않는지, 사용자 입력이 그대로 문자로 표시되는지 테스트한다.
- 화면이 있는 기능은 G3 시나리오와 G5 디자인 게이트를 통과한다.
- 순수 로직 테스트와 실제 Windows에 닿는 통합 테스트를 분리한다. 측정 로직은 시계, 근거 수집, 저장을 바꿔 끼울 수 있게 만든다.

## 7. 디자인

### 7.1 방향

**"유리와 빛으로 만든 계기판."** 어두운 공간에 빛이 흐르고, 그 위에 유리 패널이 떠 있다. 네트워크 상태가 숫자보다 먼저 빛과 움직임으로 느껴진다.

- 애플의 Liquid Glass 계열 재질을 쓴다: 뒤가 비치고 흐려지는 패널, 위쪽이 밝은 하이라이트 테두리, 은은한 광택.
- 다크가 기본이다. 라이트는 같은 구조의 다른 값이다.
- 화려하되 읽힌다. 화려함은 배경, 유리, 빛, 움직임에 싣고, 숫자와 그래프의 가독성은 양보하지 않는다.

### 7.2 층 구조

애플 가이드는 유리를 콘텐츠가 아니라 그 위에 뜬 컨트롤 층에 쓰라고 한다. 그래프와 숫자 위에 얇은 유리를 깔면 읽히지 않기 때문이다. 이 원칙을 지키면서 화면 전체가 유리로 느껴지게, 층마다 유리의 두께를 달리한다.

| 층 | 무엇이 있나 | 재질 |
| --- | --- | --- |
| 배경 | 천천히 흐르는 빛의 그라디언트. 네트워크 상태에 따라 색이 변함 | 빛 자체 |
| 콘텐츠 | 타임라인, 수치 카드, 표, 경로 맵 | **두꺼운 유리**: 강한 블러와 짙은 틴트. 뒤의 빛이 번져 보이지만 글자 대비는 보장 |
| 컨트롤 | 탐색 바, 도구 막대, 버튼, 탭 | **보통 유리**: 뒤 콘텐츠가 비치고 흐려짐 |
| 떠 있는 것 (글이 적음) | 펼침 메뉴, 도움말 풍선, 장식 요소 | **얇은 유리**: 가장 투명하고 그림자가 깊음 |
| 떠 있는 것 (글이 많음) | 대화상자, 알림, 트레이 패널 | **보통 유리 + 차폐층**: 뒤 화면을 어둡게 가려 글이 읽히게 함 |

규칙:
- 콘텐츠 층의 유리에는 **최소 불투명도**를 둔다. 뒤의 빛이 아무리 밝거나 움직여도 표면의 밝기가 일정 범위를 벗어나지 않는다.
- 유리는 **두 단까지만** 겹친다. 겹칠 때는 두께 단계가 달라야 한다.
- 틴트는 둘로 나눈다. 재질의 바탕이 되는 중립색 틴트는 두께에 따라 정해져 있고, 색이 있는 틴트는 주요 행동과 상태 표시에만 쓴다.
- 모서리 반경은 바깥 컨테이너와 동심으로 맞춘다.
- 굴절이나 색 분산처럼 계산으로 대비를 보장하기 어려운 효과는 글자가 없는 곳(가장자리, 배경, 장식)에만 쓴다.

### 7.3 색과 테마

- **다크**: 순수 검정이 아니라 깊은 남색·숯색 바탕. 높이 올라온 표면일수록 밝다.
- **라이트**: 밝은 바탕에 유리가 흰 서리처럼 얹힌다. 다크의 색을 뒤집는 것이 아니라 따로 조정한 값이다.
- **기본값**: 첫 실행은 다크. 설정에서 다크 / 라이트 / Windows 설정 따르기를 고르고, 선택을 기억한다.
- **상태색**: 정상, 주의, 끊김. 색만으로 전달하지 않고 아이콘과 글자를 함께 쓴다.
- **대비**: 본문 4.5:1 이상, 큰 글자와 그래프 선 3:1 이상. 유리 위 글자는 **허용된 배경 범위 안에서 가장 불리한 경우**로 계산한다. 배경 빛이 가질 수 있는 색과 밝기의 범위를 토큰으로 정해 두고, 재질의 틴트와 불투명도를 합성한 결과에 글자색을 대어 본다.
- **토큰**: 모든 색, 재질, 간격, 반경, 시간은 이름 붙은 토큰으로 정의한다. 화면 코드에 값을 직접 쓰지 않는다.

테마 전환은 그 자체가 연출이다. 누른 지점에서 새 테마가 퍼져 나간다.

### 7.4 모션

**원칙**

- 움직임에는 이유가 있다: 어디서 왔고 어디로 가는지, 무엇이 바뀌었는지를 알려준다.
- 빠르게 시작해 부드럽게 멈춘다. 기다리게 하지 않는다.
- 화면 요소의 배치 애니메이션은 위치, 크기 변환, 투명도만 움직인다. 배치를 다시 계산하게 만드는 속성은 움직이지 않는다.
- 그래프의 데이터 갱신, 배경 빛의 색 변화, 테마 전환의 원형 확산은 이 규칙의 예외다. 예외는 여기 적힌 것으로 한정하고 각각 프레임 기준을 지킨다.

**기준 수치** (Windows 11 모션 지침. M2에서 토큰으로 확정)

| 용도 | 시간 | 곡선 |
| --- | --- | --- |
| 요소 등장 | 167 / 250 / 333 ms | `cubic-bezier(0, 0, 0, 1)` |
| 있던 요소의 이동 | 167 / 250 / 333 ms | `cubic-bezier(0.55, 0.55, 0, 1)` |
| 퇴장 | 167 ms | `cubic-bezier(0, 0, 0, 1)` + 페이드 |
| 페이드 | 83 ms | 선형 |

**넣는 모션**

| 모션 | 내용 |
| --- | --- |
| 화면 전환 | 탐색할 때 공통 요소는 자리를 이어받아 이동하고, 나머지는 교차 페이드 |
| 차례로 등장 | 카드와 목록이 짧은 시차를 두고 올라옴 |
| 살아 있는 타임라인 | 새 측정값이 매초 부드럽게 밀려 들어옴 |
| 숫자 변화 | 수치가 바뀔 때 자릿수가 굴러감 |
| 펄스 | 측정을 시작하면 심박선이 화면을 가로지름. 앱 이름에 맞춘 대표 연출 |
| 상태 반응 | 끊김이 감지되면 배경의 빛이 붉게 물들고 경로 맵의 해당 구간이 깜빡임. 회복되면 원래 색으로 돌아옴 |
| 유리의 반응 | 포인터를 올리면 하이라이트가 포인터를 따라감. 누르면 살짝 가라앉음 |
| 테마 전환 | 누른 지점에서 원형으로 퍼짐 |
| 로딩 | 빈 화면 대신 유리 윤곽이 은은하게 빛남 |

실시간 화면은 초당 60프레임을 목표로 한다. 기준값은 M2에서 이 PC의 실측으로 정한다.

### 7.5 화면 구조와 UX

**창 하나, 탐색으로 이동한다.** 별도 모달 창을 띄우지 않는다.

| 화면 | 내용 |
| --- | --- |
| 홈 | 지금 상태 한 줄, 경로 맵, 측정 시작 버튼, 최근 측정 |
| 측정 | 겹침 타임라인, 대상별 카드, 증상 표시와 메모 |
| 진단 | 빠른 진단, 안내형 결과, 사이트 점검 |
| 기록 | 측정 목록, 등급, 끊김 목록과 통계, 분석, 비교 |
| 리포트 | 미리 보기, 가리기 옵션, 내보내기 |
| 설정 | 테마, 대상과 프로필, 알림, 저장 위치 |

**UX 원칙**

- **결론 먼저.** 등급과 한 문장을 가장 크게, 근거는 펼쳐서 본다.
- **한 번에 시작.** 첫 실행에서 자동 탐지 결과를 보여주고 바로 측정한다.
- **모든 상태를 디자인한다.** 화면마다 빈 상태, 불러오는 중, 정상, 문제 발생, 오류를 따로 정의한다.
- **전문 용어를 풀어 쓴다.** "패킷 손실 2.1%" 옆에 "100번 중 2번 응답이 없었습니다"를 둔다.
- **되돌릴 수 있게.** 시스템을 바꾸는 동작(DNS 캐시 비우기)만 확인을 묻는다.
- **키보드로 전부 조작된다.** 초점 표시가 유리 위에서도 분명히 보인다.

### 7.6 접근성과 대체 동작

화려함은 꺼질 수 있어야 한다.

| Windows 설정이나 상황 | 앱의 동작 |
| --- | --- |
| 투명 효과 끔, 배터리 절약 | 유리를 불투명한 표면으로 바꿈. 구성과 색은 유지 |
| 고대비 | 시스템 고대비 색을 따름. 배경 빛과 유리를 끔 |
| 애니메이션 끔 | 이동과 크기 변환을 빼고 짧은 페이드만 남김. 배경 빛은 정지. 깜빡임, 숫자 굴림, 포인터를 따라가는 하이라이트, 펄스도 끔 |
| 그래픽 성능이 낮아 프레임이 떨어짐 | 블러 강도를 낮추고 배경 움직임을 멈춤 |

설정 화면에도 같은 선택지를 둔다: 효과 줄이기, 움직임 줄이기.

### 7.7 결정 게이트 D2: 디자인 방향

미감은 글로 합의할 수 없다. M0에서 **같은 홈 화면을 세 가지 방향으로** 실제로 움직이는 시안으로 만들어 보여준다. 다크와 라이트 모두 만든다.

| 시안 | 느낌 |
| --- | --- |
| 오로라 | 깊은 남색 위로 청록과 보라의 빛이 흐름. 유리에 색이 번지고 강조색이 네온처럼 빛남. 가장 화려함 |
| 흑요석 | 거의 검은 바탕에 얇고 날카로운 유리. 강조색 하나. 절제된 고급스러움 |
| 프리즘 | 유리 가장자리에서 빛이 무지갯빛으로 갈라짐. 상태에 따라 배경 빛이 크게 반응 |

사용자가 하나를 고르거나 섞을 점을 말한다. 고른 시안이 이후 모든 디자인 판단의 기준이 된다. D1과 함께 한 번에 묻는다.

### 7.8 디자인 게이트 G5

화면이 있는 마일스톤마다 통과해야 한다.

**자동 검사** — 무엇을 보장하고 무엇을 보장하지 못하는지 함께 적는다.

| 검사 | 방법 | 한계 |
| --- | --- | --- |
| 토큰 밖의 값 금지 | 직접 쓴 화면 코드를 정적 검사 | 외부 차트 라이브러리 내부와 실행 중 계산되는 값은 범위를 따로 정하고 예외 목록을 둔다 |
| 대비 | 허용 배경 범위의 최악 조합을 계산. 흑백, 고채도, 강한 경계, 글자 뒤로 그래프가 지나가는 시험 장면에서 실제 화면의 색도 추출해 확인 | 모든 순간의 모든 배경을 보장하지는 못한다. 그래서 7.2의 최소 불투명도와 차폐층 규칙으로 배경의 영향을 묶어 둔다 |
| 움직임 줄이기 | 스타일로 정의한 애니메이션과 코드로 돌리는 애니메이션, 그래프 그리기까지 모든 경로에서 꺼지는지 확인 | 새 모션 경로를 추가할 때 검사 목록에도 추가해야 한다 |
| 효과 줄이기 | 속성 확인과 함께 실제 그려진 화면이 불투명한지 캡처로 확인 | |
| 프레임 | 정해진 장면, 길이, 측정 도구로 프레임 시간을 기록 | 이 PC 한 대의 값이다. 기준과 허용 편차는 M2에서 정한다 |
| 잘림과 초점 | 요소가 화면 밖으로 넘치는지, 키보드 초점이 보이는지 | |

**캡처 매트릭스** — 데모 모드에서, 같은 데이터·같은 시각·같은 창 크기로 찍는다.

- 화면 × 테마(다크, 라이트) × 그 화면에 실제로 있는 상태(빈, 불러오는 중, 정상, 문제 발생, 오류 중 해당하는 것)
- 배율 100%와 150%
- 전환 애니메이션은 연속 프레임 여러 장
- 마일스톤마다 바뀐 화면을 찍고, M11에서 전체를 찍는다.

**시각 검토**

- 사용자가 고른 시안(D2)을 기준 이미지로 `docs/design/`에 보존한다.
- Claude가 캡처를 기준 이미지와 체크리스트로 검토한다: 시안과 일치하는가, 층과 두께 규칙을 지켰는가, 글자가 읽히는가, 정렬과 간격이 맞는가, 잘림이 없는가.
- Codex에게 같은 캡처를 이미지로 보내 독립 평가를 받는다. G4 리뷰에 포함한다.
- 캡처는 PR에 싣고 사용자에게 보낸다 (4.5의 멈추지 않는 보고).

**이 게이트가 증명하지 못하는 것**

- 두 AI 모델은 미감과 가독성에서 같은 오류를 낼 수 있다.
- 정지 캡처는 체감 지연, 깜빡임, 실제로 써 볼 때의 편안함을 보여주지 못한다.
- 그래서 과업 단위 검증을 G3에 넣고(첫 측정 시작, 문제 확인, 리포트 만들기를 몇 단계에 끝내는가), 화면 품질의 최종 판단은 사용자 인수 항목으로 둔다.

**순서의 이유**

- M0에서 스택과 디자인 방향을 실물로 확인하고 정한다. 이 두 결정이 이후 전부를 좌우한다.
- 디자인 시스템(M2)을 화면보다 먼저 만든다. 화면마다 따로 꾸미면 일관성이 깨진다.
- 엔진(M3, M4)을 화면 없이 테스트로 먼저 굳힌다. 진단이 틀리면 화면이 아무리 좋아도 소용없다.
- 화면(M5~M9)은 사용자가 가장 먼저 보는 순서대로 만든다.

**M0 전용 절차**

M0에는 아직 확정된 빌드 절차도, CI도, 데모 모드도 없다. 그래서 일반 게이트 대신 아래를 쓴다.

| 게이트 | M0에서의 뜻 |
| --- | --- |
| G1 | 스파이크마다 빌드 명령과 결과를 기록 |
| G2 | 스파이크에서 검증한 것과 검증하지 못한 것을 구분해 기록 |
| G3 | 합성 데이터로 돌아가는 시험 화면을 실제로 조작. 비관리자 진단 API를 실제로 호출 |
| G5 | 완성도 평가가 아니라 후보 비교. 5절의 합격선과 측정값 |
| G4 | 기능 명세서, 스파이크 소스, 결과 보고서, 캡처를 Codex가 검토 |
| CI | 적용하지 않음. CI는 M1에서 만든다 |

- 스파이크와 시안은 `spikes/` 아래에 두고 제품 코드에 넣지 않는다.
- D1·D2의 결정 기록에는 근거가 된 스파이크의 커밋, 도구 버전, 실행 명령, 캡처를 연결한다. M1에서 `spikes/`를 지워도 git 이력에 남는다.
- 시안과 스파이크 화면에는 합성 데이터만 쓴다.
- 사용자가 D1과 D2를 컨펌하면 M0을 마감한다.

**M1 설계에서 정할 운영 세부**

- 기록 커밋을 만드는 시점, 승인받은 코드 SHA와 PR head SHA의 구분
- 재개할 때 원격 PR을 조회해 중복 생성을 피하는 방법
- G1이 만든 실행 파일을 G3에 넘기는 방법
- CI가 쌓인 PR에서도 돌도록 하는 설정
- 데모 모드의 시나리오 형식
- 화면과 본체 사이의 명령 검증 방식. 화면이 외부 사이트를 열지 않게 하는 규칙 (A안일 때)

**M3 설계에서 정할 데이터 계약**

- 버전 있는 세션 기록: 대상의 역할·주소·순서, 프로필, 측정 주기, 당시 경로, 판정 알고리즘 버전
- 빠른 진단 결과와 세션의 연결, 실행하지 않은 검사의 표시, 사용자 메모
- 중간에 끊긴 기록의 복구, 시계 변경과 절전으로 생긴 공백의 표시
- 두 측정을 비교할 수 있는 조건

**M11이 끝나면** 루프는 "완료, 사용자 인수·머지·Release 승인 대기"로 보고한다.

## 10. 사용자 확인이 필요한 항목

**이 기획서를 확정하면 아래 기본값을 모두 승인한 것으로 본다.** 바꾸고 싶은 항목은 확정 전에 말한다.

1. 6절의 기능 구분: N1~N9, N13, N14는 필수이고 N10~N12는 선택이다.
2. 6절의 "넣지 않는 것". 특히 기존 앱이 만든 측정 결과는 새 앱에서 열리지 않는다.
3. 창 하나에서 탐색으로 이동하는 구조(7.5절).
4. 같은 저장소에서 새로 만든다. 기존 소스는 `legacy/`로 옮겼다가 M10에서 지운다.
5. "설치 없이"의 뜻(5절): Windows 11 대상, 설치 프로그램 없음, Windows 11 기본 런타임 사용 허용, 파일 하나가 아니라 폴더여도 됨.
6. PR은 쌓는 방식이고 `main` 머지는 사용자가 한다.
7. 루프 기록(`docs/loop/`)과 데모 모드 캡처를 공개 저장소에 커밋한다. Codex 원문과 실제 네트워크 캡처(`.loop/`)는 커밋하지 않는다.
8. 앱 이름은 NetPulse를 유지한다.

D1(기술 스택)과 D2(디자인 방향)는 M0의 스파이크와 시안을 보고 따로 정한다.
