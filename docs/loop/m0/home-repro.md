# 흑요석 홈 시안의 WinUI 3 재현 (D1 확정 전 확인)

- 목적: 사용자가 C(WinUI 3)를 조건부로 고르면서, 고른 흑요석 시안을 C로 같은 품질로 낼 수 있는지 확인한다 (`DECISIONS.md` "D1 조건부 선호").
- 소스: `spikes/c-winui/HomeWindow.cs` (`NetPulseSpikeC.exe --home`). 시안: `spikes/design/home-mockups.html`.
- 측정 출처는 아래 "측정" 절에 적었다.
- 비교 이미지: `home-repro/compare-*.png` (왼쪽 시안, 오른쪽 C, 둘 다 1440×900), `home-repro/compare-transition.png` (테마 전환 네 시점)

| 요소 | 방법 | 상태 |
| --- | --- | --- |
| 흑요석 색·글꼴 | 시안의 토큰 값을 그대로 옮김. Pretendard를 실행 파일 옆 `Fonts`에서 읽음 | 일치 |

| 배경 빛과 흐름 | 가장자리가 투명한 원형 그라디언트 + Storyboard 이동 | 근사 (CSS blur 대신 그라디언트) |

| 끊김 상태 | 배경 빛 색, 경로 붉은 깜빡임, 등급 D, 진단 칩, 제목 | 일치 |

## 측정 (단일 실행, 앱 내부 계측)

`spikes/tools/run-home-bench.ps1`. 연한 오로라를 켠 다크 화면에서, 1초 주기 루프백 Ping 측정 루프를 함께 돌렸다.
실행 파일은 `HomeWindow.cs`가 마지막으로 바뀐 커밋 `b772cdc`의 소스로 빌드했고, 벤치는 커밋 `d4f4c49`(측정 스크립트만 추가 변경)의 깨끗한 작업트리에서 돌렸다. 원본 `.loop/logs/m0-home2/` (커밋 제외, 자원 표본 원본 `resources-*.json` 포함).

| 구간 | 평균 fps | 95백분위 프레임 간격 | 최대 프레임 간격 |
| --- | --- | --- | --- |
| 정지 장면 10초 | 164.6 | 6.2 ms | 15.8 ms |
| 오로라 켜고 끄기 6회 | 164.6 | 6.2 ms | 11.3 ms |
| 원형 전환 20회 | 152.9 | 6.3 ms | **83.4 ms** |
| 전환 뒤 정지 장면 10초 | 164.3 | 6.2 ms | 16.5 ms |

프레임 간격은 `CompositionTarget.Rendering` 콜백 사이 시간이다. 모니터에 실제로 표시된 프레임과 같지 않을 수 있다.

| 자원 (10초 표본, 프로세스 1개) | 전환 전 | 전환 도중 (두 장면이 겹치는 구간 포함) | 전환 20회 뒤 |
| --- | --- | --- | --- |
| CPU (전체 코어 기준) | 5.06% | 7.55% | 5.80% |
| 작업 집합 최대 | 163.1 MB | 194.0 MB | 193.3 MB |
| 전용 작업 집합 최대 | 55.7 MB | 82.6 MB | 81.7 MB |

| 전환 전후 상태 | 전환 전 | 전환 20회 뒤 |
| --- | --- | --- |
| 관리 메모리 (강제 수집 뒤) | 0.7 MB | 1.0 MB |
| 남아 있는 장면 / 그래프 / 애니메이션 묶음 | 1 / 1 / 1 | 1 / 1 / 1 |

- 측정 루프: 0~58번 59회차, 중복·누락 0, 예정 대비 지연 최대 14.6 ms. 화면 전환이 측정을 흐트러뜨리지 않았다.
- 전환 시간 (벤치 20회): 애니메이션 시작 호출까지 31~59 ms, 끝까지 633~672 ms. 앱이 기록한 호출 시각이고, 첫 표시 프레임의 지연은 아니다. UI Automation으로 버튼을 눌러 일으킨 전환은 끝까지 906~980 ms가 걸렸다(별도 시험). 위 값을 모든 조작의 보장값으로 볼 수 없다.
- **최대 83.4 ms의 콜백 간격**이 전환 구간에 있다. 몇 번 생겼는지와 원인은 기록하지 않았다. 새 장면 전체를 만드는 순간으로 **추정**한다. 제품에서는 테마를 바꿀 때 장면을 통째로 다시 만들지 않는 방식으로 설계한다 (M2).
- **메모리**: 전환 뒤 작업 집합 최대가 약 30 MB, 전용 작업 집합 최대가 약 26 MB 늘었다(서로 다른 10초 구간의 최대값 차이). 관리 메모리는 0.7→1.0 MB로 소폭 늘었다. 네이티브 캐시일 가능성이 있지만 **미확정**이다. 누수가 아니라는 증명은 아니며, 장시간 추세는 M2 이후에 잰다.
  - 원인 하나는 찾아 고쳤다: 떼어 낸 장면의 무한 반복 애니메이션이 계속 돌았다. 장면마다 애니메이션을 기록해 뗄 때 멈춘다.
- 자원은 스파이크 합격선(CPU 15%, 메모리 400 MB) 안이다. 이 화면은 스파이크 시험 장면보다 CPU를 더 쓴다(약 2% → 5~8%). 움직이는 요소가 많기 때문이다.

## 전환 중 자동화 격리와 빠른 연속 조작

| 시점 | `verdict` (control view / 전체) | `theme-light` 버튼 |
| --- | --- | --- |
| 전환 전 | 1 / 1 | 1 |
| 전환 시작 150 ms 뒤 (두 장면이 함께 있음) | 1 / 1 | 1 |
| 전환 뒤 | 1 / 1 | 1 |
| 빠른 연속 조작 뒤 | 1 / 1 | 1 |

- 전환 뒤 키보드 초점은 새 장면의 같은 버튼에 있다.
- 빠른 연속 조작(전환 진행 중 다른 전환 누르기, 오로라 세 번): 앱 유지. 진행 중이던 전환 때문에 전환 요청 1건은 무시됐다(기록됨). 오로라는 누른 순서대로 켜짐·꺼짐·켜짐. 스크립트는 80 ms를 기다리고 눌렀지만 UI Automation 호출 지연 때문에 앱이 받은 오로라 간격은 약 485·226 ms였다. 수십 ms 간격의 실제 입력은 시험하지 못했다.
- 전환 중 이전 장면의 그래프는 자기 테마색을 유지한다 (그래프마다 만들 때의 테마를 기억).
- 화면 읽기 프로그램으로는 확인하지 않았다.

## 남은 차이와 확인하지 못한 것

- 연한 오로라의 세기·위치, 라이트 그림자 세기 (위).
- 흑요석 시안의 미세한 결(점 무늬 질감)은 옮기지 않았다.
- 타임라인 두 그래프가 같은 색인 것은 시안 그대로다. M2에서 보조 계열색을 정한다 (`DECISIONS.md` D2).
- 대비 계산(오로라를 켠 가장 불리한 배경 포함), 고대비 실제 화면, 키보드 탐색, 화면 읽기, 다른 배율, 장시간 실행.
- Windows 설정은 읽도록 했지만 이 PC의 설정을 바꿔 시험하지는 않았다 (사용자 시스템 설정).
