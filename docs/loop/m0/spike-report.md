### P1 창 안쪽 유리 — 캡처 판정

`spike/a-net10-glass-test.png`, `spike/c-glass-test.png`. 6 px 간격 흑백 줄무늬 위에 같은 12% 틴트의 패널 셋을 나란히 놓았다.

- **틴트만**: 두 안 모두 줄무늬가 선명하게 비친다.
- **블러 / Acrylic**: 두 안 모두 줄무늬가 회색으로 뭉개진다. 창 안쪽에서 뒤 콘텐츠를 실제로 흐린다는 증거다.
- **불투명**: 두 안 모두 줄무늬가 가려진다.

**차이**: A는 패널마다 블러 강도를 정할 수 있다(`backdrop-filter: blur(Npx)`). C의 `AcrylicBrush`에는 블러 강도 속성이 없다. WinUI 2.6.5 투영 어셈블리의 속성 이름에서 `Tint*`, `Fallback*`, `AlwaysUseFallback`만 찾았다. C에서 강도를 바꾸려면 Composition 효과를 직접 짜야 하고, 이것은 시험하지 않았다.

### P3 메모리 — 불합격의 내용

- A는 WebView2가 프로세스 7개를 띄운다. 작업 집합 합계의 10초 최대값이 합격선 400 MB를 넘었다 (A-net10 570 MB, A-net48 488 MB).
- 작업 집합 합계는 프로세스 사이 공유 페이지를 여러 번 센다. 공유분을 뺀 전용 작업 집합도 보조로 쟀다 (A-net10 최대 211 MB, A-net48 168 MB, C 41 MB). 전용 작업 집합도 앱의 전체 메모리 비용과 같지는 않다.
- **합격선은 측정 전에 정한 그대로 적용했다.** 이 기준을 완화할지는 사용자 결정 사항으로 올린다.
- 본체를 .NET Framework 4.8로 바꾸면 약 80 MB 줄지만 합격선 아래로는 내려가지 않는다. 대부분이 WebView2 몫이다.

### P9 대체 동작 — 캡처와 코드 판정

- 설정 읽기: Windows의 앱 테마, 투명 효과, 애니메이션 설정을 읽었다. 이 PC는 셋 다 켜짐이다. Windows 설정 자체를 바꾸는 시험은 하지 않았다.
- 불투명 표면: `spike/a-net10-reduced.png`, `spike/c-reduced.png`. 강제 옵션으로 투명 효과를 끈 화면이다. 배경 빛이 사라지고 패널이 불투명하다.
- 이동 없음: 움직임 줄이기에서 CSS·Storyboard 애니메이션, 그래프 흐름, 포인터를 따라가는 빛을 모두 끄도록 고쳤다(1차 검토 지적). 0.4초 간격 두 캡처를 비교하니 바뀐 화소는 그래프와 수치 영역 안에만 있었고, 배경과 탐색 막대는 그대로였다. 그 사이 새 회차 값이 들어와 그래프와 수치가 한 번에 바뀐 것으로 본다. 이 판단은 화소 위치에 근거한 추정이고, 회차 도착 시각과 대조하지는 않았다.

### 항목별 메모

- **P2**: 세 후보 모두 화면 주사율(165 Hz)에 붙어 이 장면으로는 차이가 나지 않았다. 측정 방식은 다르다. A는 웹 화면의 `requestAnimationFrame`, C는 `CompositionTarget.Rendering` 간격이다. 둘 다 앱이 받는 프레임 콜백이고 화면에 실제로 표시된 프레임과 같지 않을 수 있다.
- **P4**: 장면을 돌리며 75초 동안 76회차를 기록했다. 회차마다 예정·실제 시각을 남겨 중복·누락·지연을 원본에서 계산했다.
- **P5**: 30초 숨긴 뒤 다시 보인 순간부터 100 ms마다 화면의 회차 번호를 읽어, 복귀 시점의 최신 회차가 표시될 때까지 걸린 시간을 쟀다.
- **P6**: 세 후보 모두 ICMP, 시스템 이벤트 로그 읽기, 최적 인터페이스 조회, 인터페이스 상태 읽기가 됐다. **A-net48은 인터페이스를 .NET 10보다 훨씬 적게 열거했다**(로그에 개수 기록, 화면에는 표시하지 않음). 원인은 확인하지 않았다. 제품 엔진(M3·M4)에서 인터페이스 관측을 설계할 때 확인할 항목이다.
- **P7**: 첫 실행은 사용자 데이터 폴더를 지운 상태에서 쟀다. C의 첫 실행이 1.76초로 가장 느리다. 단일 파일이 처음에 내용을 푸는 시간으로 추정한다. 쓰기 금지 폴더(파일 만들기·쓰기 거부)에서 세 후보 모두 시작했다.
- **P8**: A는 WebView2 원격 디버깅 포트를 자동화 실행에서만 열고 Playwright로 붙었다. C는 Windows UI Automation으로 조작했고, 이를 위해 코드에서 만든 컨트롤마다 AutomationId를 붙였다. 한글 입력은 두 안 모두 유니코드 문자 입력으로만 확인했다. 입력기 조합은 확인하지 않았다.

## 스파이크 중 발견한 것

`DECISIONS.md` "스파이크 진행 중 발견"과 "M0 G4 1라운드"에 자세히 적었다. 제품 설계로 넘길 것:

1. 측정 루프가 타이머가 일찍 깨면 같은 회차를 두 번 기록했다. 고쳤고, 제품 엔진(M3)의 테스트 항목이다.
2. C에서 첫 측정값이 화면 배치보다 먼저 오면 null 참조로 앱이 종료됐다. 측정과 화면의 준비 순서를 제품에서 명시적으로 다뤄야 한다. 이 버그를 모르는 동안 "C는 단일 파일 배포가 안 된다"는 틀린 결론을 한때 적었다가 바로잡았다.
3. 사용자 데이터 폴더가 없는 첫 실행 경로를 시험에 넣어야 한다. 1차 검토에서 C의 진단 기록 코드가 이 경로에서 실패할 수 있다는 지적을 받고 고쳤다.
4. .NET Framework 4.8과 .NET 10의 인터페이스 열거 결과가 다르다.

## 결정 요청 (D1)

합격선을 그대로 적용하면 **C만 합격**이다. A가 떨어진 이유는 메모리 한 항목이고, A가 요구의 중심(화려한 유리와 모션)에서 더 자유롭다. 그래서 두 길을 나란히 올린다.

| | C로 간다 (합격선대로) | A로 간다 (메모리 기준을 사용자가 완화) |
| --- | --- | --- |
| 장점 | 가볍다 (CPU 약 2%, 메모리 약 146 MB, 프로세스 1개). 측정한 모든 항목 통과 | 유리·광택·전환을 가장 자유롭게. 디자인 시안을 그대로 옮김. A-net48이면 배포 1.1 MB |
| 단점 | 블러 강도 고정, 고급 효과는 Composition으로 직접 작성. 시안 재현에 품이 듦 | 메모리 490~570 MB (전용 170~210 MB), 프로세스 7개. 상주 앱으로는 무거움 |
| 위험 | 고른 시안의 무지갯빛 테두리·원형 확산·흐르는 빛을 같은 품질로 낼 수 있는지 **미확인** | 하루 종일 켜 둘 때의 체감 부담. 장시간 메모리 증가는 재지 않음 |
| 확정 전 추가 확인 | 고른 시안의 대표 카드·유리 겹침·테마 전환을 C로 재현해 비교 (M0 안에서) | 사용자가 승인한 새 메모리 예산을 기록하고, 그 예산으로 다시 판정 |

## 이 스파이크가 증명하지 못한 것

- 프레임은 165 Hz 화면 한 대의 값이다. 저사양 PC, 60 Hz 화면, 배율 150%는 재지 않았다.
- 장시간(몇 시간) 실행의 메모리 증가와 숨김 상태의 자원 사용은 재지 않았다.
- C의 Composition 효과로 시안 수준의 표현이 나오는지는 만들어 보지 않았다.
- A의 투명 웹 바탕과 창 뒤 Mica 조합은 시험하지 않았다.
- 실제 Windows 설정(투명 효과·애니메이션·고대비)을 바꾼 동작, 입력기 조합.
