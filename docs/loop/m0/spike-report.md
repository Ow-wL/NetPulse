# M0 스파이크 결과 보고서

- 측정일: 2026-11-13
- 환경: Windows 11 빌드 26300, 165 Hz 화면, 배율 100%, 관리자 권한 없음
- 합격선: `docs/loop/DECISIONS.md` "M0 스파이크 합격선" (측정 전에 커밋 `875dd28`로 기록)
- 원본 로그: `.loop/logs/m0/` (커밋 제외. 이 PC의 실행 기록이라서다)

## 후보

| 이름 | 구성 | 배포 형태 |
| --- | --- | --- |
| A-net10 | WinForms 창 + WebView2(웹 화면) + .NET 10 본체 | 자체 포함 단일 exe + `web` 폴더 |
| A-net48 | 같은 코드, 본체만 Windows 내장 .NET Framework 4.8 | exe + DLL 4개 + `web` 폴더 |
| C | WinUI 3 (Windows App SDK 2.6.5), .NET 10 | 자체 포함 단일 exe + 리소스 2개 |

세 후보가 같은 측정 루프(`spikes/shared/SpikeCore.cs`)를 쓰고, 같은 시험 장면을 그린다. 측정과 조작은 스크립트 하나로 돈다(`spikes/tools/run-spike-a.ps1`, `run-spike-c.ps1`).

### 항목별 메모

**P1 창 안쪽 유리** (`spike/p1-compare.png`, 왼쪽 A, 오른쪽 C)
- 기본 장면은 틴트가 진해 얇은 선이 거의 사라져 판정이 어려웠다. 틴트를 12%로 낮춘 확인 모드를 따로 돌렸다. 두 안 모두 패널 뒤의 배경 빛이 번져 비치고 선은 흐려져 사라진다. 투명하기만 하고 흐리지 않았다면 선이 선명하게 보였을 것이다.
- **차이**: A는 패널마다 블러 강도를 정할 수 있다(`backdrop-filter: blur(Npx)`). C의 `AcrylicBrush`에는 블러 강도 속성이 없다. WinUI 2.6.5 투영 어셈블리에서 `Tint*`, `Fallback*`, `AlwaysUseFallback`만 확인했다. C에서 강도를 바꾸려면 Composition 효과를 직접 짜야 하고, 이것은 시험하지 않았다.

**P2 프레임**: 세 후보 모두 화면 주사율(165 Hz)에 붙었다. 이 장면으로는 차이가 나지 않았다. 측정 방식이 다르다는 점은 남는다. A는 웹 화면의 `requestAnimationFrame`, C는 `CompositionTarget.Rendering` 간격이다.

**P3 메모리**
- A는 WebView2가 브라우저·GPU·렌더러 등 프로세스 7개를 띄운다. 작업 집합 합계는 공유 페이지를 여러 번 센다. 그래서 공유분을 뺀 전용 작업 집합을 보조로 쟀다(A 181~224 MB, C 41 MB).
- **합격선은 측정 전에 정한 그대로 적용한다.** 이 기준이 적절했는지는 사용자 결정 사항으로 올린다(아래 "결정 요청").
- 본체를 .NET Framework 4.8로 바꿔도 74 MB 줄어드는 데 그쳤다. 대부분이 WebView2 몫이다.

**P6 진단 API**: 세 후보 모두 ICMP, 시스템 이벤트 로그 읽기, 최적 인터페이스 조회, 인터페이스 상태 읽기가 됐다. **A-net48에서는 인터페이스 수가 5개로 나왔다**(.NET 10은 57개). .NET Framework가 일부 인터페이스를 다르게 열거하는 것으로 보인다. 원인은 확인하지 않았다. 제품 엔진(M3·M4)에서 인터페이스 관측을 설계할 때 확인할 항목이다.

**P7 배포**
- A-net48이 가장 작다(1.1 MB). Windows 11에 들어 있는 .NET Framework와 WebView2를 쓰기 때문이다.
- C는 단일 파일로 만들려면 `EnableMsixTooling`이 필요하다. 그래도 `App.xbf`와 앱 `.pri`가 exe 옆에 따로 남는다.
- 시작 시간은 프로세스 시작부터 첫 화면 프레임까지다.

**P8 자동화**
- A: WebView2에 원격 디버깅 포트를 열어 Playwright로 붙었다. 포트는 자동화 실행에서만 연다.
- C: Windows UI Automation으로 버튼을 누르고, 글자를 읽고, 한글을 입력했다. 이를 위해 C# 코드에서 만든 컨트롤마다 AutomationId를 붙였다.
- 한글 입력은 두 안 모두 유니코드 문자 입력으로만 확인했다. 입력기 조합은 확인하지 않았다.

**P9 대체 동작**: Windows의 앱 테마, 투명 효과, 애니메이션 설정을 레지스트리와 시스템 매개변수로 읽었다. 이 PC는 셋 다 켜짐이다. 끄는 경우의 화면은 앱 강제 옵션으로 만들었다(`spike/a-net10-reduced.png`, `spike/c-winui-reduced.png`). Windows 설정 자체를 바꾸는 시험은 하지 않았다.

## 표현력 비교 (합격선 밖, 추천 근거)

| | A (웹 화면) | C (WinUI 3) |
| --- | --- | --- |
| 유리 블러 강도 | 패널마다 자유 | 고정. 바꾸려면 Composition 효과를 직접 작성 |

| 테마 원형 확산 | View Transitions로 구현함 | 구현 안 함. 짧은 교차 페이드로 대신함 |

| 창 뒤 Mica | 호출은 성공, 화면 바탕이 불투명해 안 보임 | 동작 |
| 디자인 시안 재현 | 시안이 웹 기술이라 그대로 옮김 | 시안을 XAML과 Composition으로 다시 만들어야 함 |

## 스파이크 중 발견한 것

`DECISIONS.md` "스파이크 진행 중 발견"에 자세히 적었다. 요약:

1. 측정 루프가 타이머가 일찍 깨면 같은 회차를 두 번 기록했다. 고쳤고, 제품 엔진의 테스트 항목으로 넘긴다.
2. C에서 첫 측정값이 화면 배치보다 먼저 오면 null 참조로 앱이 종료됐다. 고쳤다.
   - 이 버그를 모르는 동안 "C는 단일 파일 배포가 안 된다"는 틀린 결론을 한때 적었다가 바로잡았다.
   - 제품 설계에 주는 교훈: 측정과 화면의 준비 순서를 명시적으로 다뤄야 한다.
3. A-net48과 A-net10의 인터페이스 열거 결과가 다르다.

## 결정 요청 (D1)

합격선을 그대로 적용하면 **C만 합격**이다. 다만 A가 떨어진 이유는 메모리 한 항목이고, A가 요구의 중심(화려한 유리와 모션)에서 더 자유롭다. 그래서 두 길을 나란히 올린다.

| | C로 간다 (합격선대로) | A로 간다 (메모리 기준 완화) |
| --- | --- | --- |
| 장점 | 가볍다 (CPU 1.6%, 메모리 146 MB, 프로세스 1개). 측정한 모든 항목 통과 | 유리·광택·전환을 가장 자유롭게. 디자인 시안을 그대로 옮김. A-net48이면 배포 1.1 MB |
| 단점 | 블러 강도 고정, 고급 효과는 Composition으로 직접 작성. 시안 재현에 품이 듦 | 메모리 500~580 MB (전용 180~220 MB), 프로세스 7개. 상주 모니터링 앱으로는 무거움 |
| 위험 | 시안의 무지갯빛 테두리·원형 확산을 같은 품질로 낼 수 있는지 미확인 | 사용자가 하루 종일 켜 둘 때의 체감 부담 |

Claude 추천과 Codex 의견은 결정 요청 메시지에 함께 적는다.

## 이 스파이크가 증명하지 못한 것

- 프레임은 165 Hz 화면 한 대의 값이다. 저사양 PC, 60 Hz 화면, 배율 150%는 재지 않았다.
- 장시간(몇 시간) 실행의 메모리 증가는 재지 않았다.
- C의 Composition 효과로 시안 수준의 표현이 나오는지는 만들어 보지 않았다.
- A의 투명 웹 바탕과 창 뒤 Mica 조합은 시험하지 않았다.
