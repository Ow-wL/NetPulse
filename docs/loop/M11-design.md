## 3. 설계

### A. 완성 정의 점검 (`M11-completion.md`)

- 1절 표: 기능 | 수용 기준(기획서 6절 문장 그대로 요약, 문장을 부분으로 나눔) | 구현 마일스톤 | 증거(시험 클래스·메서드, 장면 ID, 파일:줄) | 상태. 조사 결과(23개 중 20개 증명, F7·R1·R2 부분) 위에 B의 새 시험을 넣어 다시 채운다.
- 상태는 네 가지로 나눠 섞지 않는다 [1-3]:
  - **증명됨**: 그 수용 기준의 각 부분에 대응하는 단언이 있는 시험이 최종 게이트에서 통과했다. 실제 네트워크 성공 여부는 판정하지 않는다(기획서 4절).
  - **미검증**: 기준의 일부에 증거가 없다 (그 부분을 적는다).
  - **한계(사전 인정)**: 기획서·설계가 미리 인정한 환경 한계 (예: 150%는 시뮬레이션, 실제 DPI는 인수). 그 부분과 인수 항목 번호를 적는다.
  - **사용자 결정으로 바뀜**: 범위가 결정으로 달라진 것 (결정 원문 위치).
- 기능 하나가 여러 상태를 가질 수 있다 (예: R2 = 유선 증명됨 + Wi‑Fi 해석 증명됨 + Wi‑Fi 하드웨어 미검증 → 인수 항목).
- 완성 조건 2~6도 같은 문서에 한 절씩: 근거 위치와 최종 커밋의 결과.
- 조건 5 "각 마일스톤의 PR": M0~M4는 옛 비공개 저장소(`Ow-wL/NetPulse-private`)의 PR, M5~M10은 공개 저장소 PR #1~#6. 번호가 겹치므로(STATE "저장소 이전" 설명에 이미 있음) 완성 문서에는 PR마다 저장소 이름을 붙여 적는다.

### B. 증거가 빈 필수 기능

| 항목 | 빈 곳 | 채우는 방법 |
| --- | --- | --- |
| **B1** F7 Windows 설정 열기 | `diagnose.settings.network/wifi/proxy`, `diagnose.conclusion.settings`를 누르는 시험이 없다. 데모 `DemoSystemActions`가 `settings:` 호출을 기록하지만 단언이 없다 (M6 설계 1절 약속) | G3: 데모에서 각 단추를 눌러 진단 값(또는 앱 기록)의 호출 기록이 그 대상·한 번인지 본다. 실제 설정 창은 열지 않는다(데모 대체 경로). 진단 값에 호출 기록이 없으면 진단 값만 더한다 |
| **B2** R1 대상·프로필 편집 | 대상 추가·**삭제**·순서(위/아래)·사용 끄기·역할, 프로필 추가·삭제·선택, 다시 탐지를 누르는 UI 시험이 없다. 기존 `M5FlowTests`의 대상 삭제는 `profile.cancel`로 되돌려 저장 증거가 아니다 (M5 설계는 G2+G3) [1-2] | G3: 조작마다 기대 결과를 정한 표대로 편집 → 저장 → **앱을 다시 시작**해 프로필 파일과 편집기 화면이 그 기대와 같은지. 이어서 선택한 프로필로 측정을 시작해 **기록 머리의 대상 구성(활성 대상·순서·역할·방식)**이 편집 결과와 같은지. 측정 중 읽기 전용은 기존 시험 |
| **B3** R2 Wi‑Fi 링크 근거 | `LinkLogReader`의 무선 경로(WLAN 채널 질의, 이벤트 ID → 상태, XML `InterfaceGuid` 추출, 측정 어댑터와 GUID 대응, 읽을 수 없는 로그의 지원 여부)를 지나는 시험이 없고 Wi‑Fi 실측도 없다 [1-3] | **시험 경계를 뽑는다**: 무선 경로를 "이벤트 기록(Id, 시각, 이벤트 XML) 목록 + 측정 어댑터 목록 + 로그 읽기 가능 여부 → 링크 사건·어댑터별 지원 여부"를 돌려주는 순수 함수로 꺼내고, `LinkLogReader`는 실제 로그를 읽어 그 함수에 넘긴다(동작 보존 리팩터, 제품 소스 변경). G2 기대 결과: GUID 일치 → Linked, 불일치 → Unlinked, `InterfaceGuid` 누락·형식 오류 → 해석 안 됨 수, 모르는 Id → 해석 안 됨, 로그 읽을 수 없음 → 무선 어댑터 Unsupported `wlan-log-unavailable`, 이벤트 없음 → Supported·사건 0, 접근 거부 → Denied. **Wi‑Fi 하드웨어 실측은 R2의 미검증 부분**으로 완성 문서에 적고 인수 항목 8로 둔다 (N11의 M12 이월을 근거로 쓰지 않는다) |
| **B4** N14 첫 측정까지 단계 수 | 동의를 포함한 단계 수를 세는 게이트 시험이 없다 (M10에서 "동의 포함 세 단계 안"으로 정함) | G3: 동의 기록 없는 데모 실행에서 사용자 조작만 세어 측정 시작까지 3단계 이하(동의 → 시작)인지 |

### C. 전 화면 디자인 총점검

- **C1 빈 장면 채우기** [1-4]: 구현 첫 단계에서 기존 장면 목록(`m5`~`m10-scenes.txt`)과 각 매트릭스 시험의 추가 장면(`Extras`)을 읽어 **화면·상태 × 대체 모드 표**를 만들어 `M11-completion.md`에 넣고, 아래 규칙으로 빈칸을 채운다 (`m11-scenes.txt` 기본 장면 + `M11MatrixTests` 추가 장면).
  - 대체 모드: 고대비 aquatic, 고대비 desert, 투명 효과 끔(다크·라이트), 움직임 줄이기(움직임이 있는 화면만), 고대비 + 150%.
  - 규칙: **모든 화면과 모든 대화상자·창**(첫 실행, 홈, 측정, 프로필 편집기, 진단, 기록 목록·상세·비교·진단 기록, 리포트, 설정, 사용 조건 창, 대화상자: 저장 안 한 변경·DNS 비우기 확인·숨김 안내·기록 옮기기 확인·라이선스와 고지)이 각 대체 모드에서 대표 상태 하나 이상을 가진다.
  - 대표 상태는 그 화면에서 **겹치는 층과 요소 종류가 가장 많은 상태**(유리 단계, 본문·흐린 글, 단추, 그래프·띠, 배너)로 정하고, 표에 장면 ID와 고른 이유를 적는다. 1판에서 빠졌던 측정 화면의 투명 효과 끔, 첫 실행·프로필의 고대비 + 150%를 포함한다.
  - 기본 장면에 없던 상태: 첫 실행 IPv4 경로 없음(`firstrun-noipv4`, 데모 `no-ipv4` — 기능 시험 `RoundTripWorksWhenTheFirstRunFindsNoIpv4Route`만 있었다)을 다크·라이트 × 100·150으로 더한다.
  - 전환 프레임: 설정 화면 진입, 동의 → 셸 전환을 기존 전환 프레임 장치로 한 묶음씩.
- **C2 화면 위 대비 측정**: 지금은 홈·진단·기록·리포트·부품 전시만 실측한다. 측정(`measure-live`, `measure-outage`), 첫 실행(`firstrun-detected`), 프로필(`profile-ok`), 설정(`settings-normal`), 사용 조건(`terms`) 장면에 같은 측정을 더한다. 측정할 요소는 장면마다 고정한다: 제목, 본문 글, 흐린 글, 단추 글, 정보 칩, 배너 글 — 그 장면에 있는 것 전부, 놓인 유리 단계별로. 다크·라이트 둘 다. 기준은 M2 토큰 기준 그대로 [1-4].
- **C3 시각 검토** [1-6]: 최종 게이트 캡처 전부(약 700장)에 대해
  - **자동 검사가 전부를 덮는다**: 매트릭스 시험의 배치 검사(잘림·글자 잘림·겹침)와 C2 대비 측정은 모든 캡처에서 이미 돈다. 그 결과를 완성 문서에 장면 수와 함께 적는다.
  - **사람 눈 검토 (Claude)**: 화면별 접촉 시트로 전체 흐름·일관성(층·두께 규칙, 정렬·간격, 시안 D2와의 일치)을 본다. 시트마다 원본 캡처 파일과 타일 위치의 대응 목록을 남긴다. **가독성·초점 표시·잘림은 원본 크기로** 본다: 상태마다 다크 150% 한 장(잘림이 가장 잘 나는 조합) + 모든 대체 모드 장면은 원본으로 연다. 판정은 화면별 표(체크리스트 항목마다 결과·근거 파일)로.
  - **Codex 독립 평가**: 같은 접촉 시트와, 원본으로 연 장면 중 화면마다 대표 원본을 이미지로 보내 D0의 증거 검토에서 받는다.
- **C4 미뤄 둔 재검토 3건** (판정만, 바꾸는 것은 사용자 확인 뒤). 각각 비교 이미지·판정 이유·후속 조치를 완성 문서에 남긴다 [1-6]:
  1. 흑요석 미세 결(M2 5.5): 시안과 나란히 비교해 "넣지 않음 유지 / 넣음" 판정. 넣는 것은 디자인 변경이라 사용자에게 묻는다.
  2. 콘텐츠를 제목 표시줄까지 넓히기(M5 4.2): 끌기·캡션 버튼·창 캡처·자동화 경계 위험이 그대로라 **넓히지 않음 유지**를 제안한다. 근거를 기록.
  3. 문구 점검(`Screens/Text.cs` 등 화면 문구 묶음): 기획서 7.5 원칙(결론 먼저, 쉬운 말, 단정하지 않음) 위반·맞춤법·용어 불일치를 목록으로. 고치는 것은 문구만이고 시험이 보는 문구는 시험과 함께 바꾼다.
- 결함이 나오면(잘림, 대비 부족, 초점 안 보임, 문구 오류) 그 화면만 고치고 해당 장면을 다시 찍는다.

### D. 맨 위 커밋에서 최종 증거

- **D0 순서** [1-1]:
  1. 구현과 중간 확인 (노트북 도구가 준비되면 노트북, 아니면 디버그 빌드의 해당 클래스만, 사용자 허락 뒤).
  2. 후보 코드 커밋 X에 G4 diff 리뷰 (3라운드 상한, 넘으면 사용자 승인 예외).
  3. 승인된 같은 X에서 **데스크톱 최종 전체 게이트** (D1).
  4. 그 게이트의 캡처·결과로 C3 시각 검토를 하고 `M11-completion.md`·`acceptance-checklist.md`를 채워 **증거 검토**를 받는다: Codex가 완성 문서의 표와 실제 게이트 결과(TRX·g5.json·캡처)가 맞는지 확인하고, 접촉 시트·대표 원본을 독립 평가한다. 문서는 `docs/loop/`라 X 뒤 기록 커밋이다. 이 검토로 G5가 확정된다.
  5. 같은 X로 깨끗한 클론(D2)과 실측 시나리오(D3).
  6. 마감 스크립트: 푸시·PR·CI.
  - **되돌아가는 조건**: 3~5에서 실패하거나 결함이 나와 제품·시험·장면을 고치면 새 X가 되고 2로 돌아간다. 환경 원인(전경 앱, 클립보드 준비, 클립보드 시험 건너뜀)으로 같은 X를 다시 돌리는 것은 허용하며 기록한다. "데스크톱 1회"는 **통과한 최종 실행이 X마다 하나**라는 뜻이고, 실패 뒤 재실행을 막지 않는다.
- **D1 최종 전체 게이트**: X에서 `build/build.ps1 -Gate` → (재부팅은 사용자 선택) → 사용자 클립보드 준비(`cmd /c "echo NetPulse| clip"`, 형식 이름만 확인) → `build/ui-test.ps1`.
- **D2 깨끗한 클론·CI**: `tools/loop/clean-clone.ps1 -Commit X`, 마감 스크립트의 PR CI.
- **D3 실측 시나리오 (게이트 밖, 공개 안 함)**: 최종 배포 exe(`artifacts/<X>/app/NetPulse.exe`)로 `Kind=Live` 시험 `M5LiveRunTests`~`M9LiveRunTests`를 돌린다. 출력은 `.loop/` 아래. 판정은 "앱이 관측한 것을 정확히 기록하고 보여주는가"(네트워크 성공은 판정 안 함). `M7LiveRunTests`는 실행 기록이 없어 처음 돈다. 풍선은 이미 사용자가 확인(M10), 이번에는 기록만.
- **D4 UI 시험의 CI 재검토 (M1 설계)**: 판정 제안 — **계속 CI에서 빼고 데스크톱 게이트로 둔다**. 근거: 834건 약 50분, 대화형 데스크톱·전경·클립보드·작업 표시줄이 필요, 노트북 실측에서 성능·타이밍 기준이 하드웨어에 따라 흔들렸다(825/834). M12의 게이트 단축과 함께 다시 볼 수 있다.

### E. 고침과 버전

- **E1 결함 처리**: 점검에서 나온 결함은 이 마일스톤에서 고친다(작은 것). 범위가 크면 사용자에게 M12로 옮길지 묻는다.
- **E2 버전** [1-5]: 0.9.0을 유지한다.
  - 게시본 `5c30ef2`와 M11 검증본 X의 버전·manifest·zip·exe SHA-256·release.json을 **나눠** 적는다 (exe 바이트는 커밋 해시가 박혀 늘 다르다).
  - 비교 범위는 **제품·배포 입력 전체**: `src/`, `Directory.Build.props`, `Directory.Packages.props`, `global.json`, `assets/`(글꼴), `demo/`(시나리오), `LICENSE`, `build/`의 배포·고지·묶기 부분(`build.ps1`, `common.ps1`, `notices.ps1`, `notices/`, `release-readme.txt`), 앱 csproj의 묶음 대상, 실제 의존성 구성(빌드의 `project.assets.json`·묶음 입력 목록 비교).
  - 차이를 셋으로 분류한다: (가) 없음, (나) 동작 보존 변경 — 시험 경계 뽑기(B3)·진단 값 추가처럼 사용자에게 보이는 동작·표시·묶음이 바뀌지 않음, 근거는 같은 시험 통과와 묶음 입력 목록 동일, (다) 동작·표시·묶음에 영향.
  - (가)이면 게시본이 그대로 유효하다고 적는다. (나)·(다)이면 차이 목록을 적고, 다시 게시할지(0.9.1)를 사용자에게 묻는다. Claude의 제안: (나)만이면 다시 게시하지 않고 1.0.0(M12)에서 낸다. B3은 제품 소스를 바꾸므로 (나)가 예상된다.

### F. 인수 체크리스트 (`acceptance-checklist.md`)

항목마다: 무엇을, 어떻게(단계), 기대 결과, 기록 칸(날짜·결과·메모). 루프가 대신할 수 없는 것만 넣는다.

6. SmartScreen 경고와 실행
7. 트레이·풍선 (실제 작업 표시줄), 트레이 메뉴 [종료]

9. 리포트를 통신사 제출용으로 열어 보기 (가린 값)
