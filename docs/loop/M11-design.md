# M11 설계 — 최종 통합

1판 · 2026-11-20 · 브랜치 `loop/m11-final` (`main` `06a3144` = M10 병합 위)

기획서 8절 M11 행: "체인 맨 위 커밋에서 전체 게이트 재실행, 전 화면 디자인 총점검, 완성 정의 점검, 검증한 파일의 버전·해시 기록, 인수 체크리스트 작성". 끝났다는 증거: 루프 완료 조건 1~6 (`docs/loop-plan.md` 1절). 그 밖에 기획서·설계서가 M11에 맡긴 일: 최종 배포 파일을 데모 없이 실측 시나리오로 확인(기획서 4절 "데모만으로 통과시키지 않는 것"), M11에서 전 화면을 찍는다(7절), UI 시험의 CI 제외 재검토(M1 설계), 흑요석 미세 결 재검토(M2 설계 5.5), 콘텐츠를 제목 표시줄까지 넓히기 재검토(M5 설계 4.2), 문구 점검(M5 설계 4.4 `Screens/Text.cs`), 깨끗한 Windows 미확인을 인수 체크리스트에(M10 설계).

M11은 **점검·증명 마일스톤**이다. 새 기능은 넣지 않는다. 점검에서 나온 결함만 고치고, 증거가 빈 곳은 시험으로 채우거나 한계로 적는다.

**사용자 결정 (DECISIONS "M10 마감, 0.9.0 게시, M12 범위", "M10 SDK 고정과 공개 버전 0.9.0")**

| 쟁점 | 결정 |
| --- | --- |
| M12로 옮긴 것 | 금융 보안 프로그램 충돌(1.0.0 조건), N11 Wi‑Fi 신호 세기, 게이트 시간 단축(C→B→A), 프레임 기준의 주사율 전제. **M11에서 하지 않는다** |
| N12 | 계속 뺀다 |
| 공개 버전 | 0.9.0은 `5c30ef2`로 이미 게시. 1.0.0은 M12 뒤 |
| 게이트 운영 | G4 라운드 중의 중간 확인은 노트북, 최종 전체 게이트는 데스크톱에서 1회 (도구는 다른 세션이 저장소 밖에서 만드는 중) |
| 화면 사용 | 화면을 쓰는 시험·게이트·캡처는 사용자에게 허락받고 PC를 비운 뒤에만 |

## 3. 설계

### A. 완성 정의 점검 (`M11-completion.md`)

- 1절 표: 기능 | 수용 기준(기획서 6절 문장 그대로 요약) | 구현 마일스톤 | 증거(시험 클래스·메서드, 장면 ID, 파일:줄) | 상태(증명됨 / 한계 있음 / 사용자 결정으로 바뀜). 조사 결과(23개 중 20개 증명, F7·R1·R2 부분) 위에 B의 새 시험을 넣어 다시 채운다.
- "증명됨"의 뜻: 그 수용 기준 문장의 각 부분에 대응하는 단언이 있는 시험이 최종 게이트에서 통과했다. 실제 네트워크 성공 여부는 판정하지 않는다(기획서 4절).
- 완성 조건 2~6도 같은 문서에 한 절씩: 근거 위치와 최종 커밋의 결과.
- 조건 5 "각 마일스톤의 PR": M0~M4는 옛 비공개 저장소(`Ow-wL/NetPulse-private`)의 PR, M5~M10은 공개 저장소 PR #1~#6. 번호가 겹치므로(STATE "저장소 이전" 설명에 이미 있음) 완성 문서에는 PR마다 저장소 이름을 붙여 적는다.

### B. 증거가 빈 필수 기능

| 항목 | 빈 곳 | 채우는 방법 |
| --- | --- | --- |
| **B1** F7 Windows 설정 열기 | `diagnose.settings.network/wifi/proxy`, `diagnose.conclusion.settings`를 누르는 시험이 없다. 데모 `DemoSystemActions`가 `settings:` 호출을 기록하지만 단언이 없다 (M6 설계 1절 약속) | G3: 데모에서 각 단추를 눌러 진단 값(또는 앱 기록)의 호출 기록이 그 대상·한 번인지 본다. 실제 설정 창은 열지 않는다(데모 대체 경로). 진단 값에 호출 기록이 없으면 진단 값만 더한다 |
| **B2** R1 대상·프로필 편집 | 대상 추가·순서(위/아래)·사용 끄기·역할, 프로필 추가·삭제·선택, 다시 탐지를 누르는 UI 시험이 없다 (M5 설계는 G2+G3) | G3 한 흐름: 편집기에서 각 조작 → 저장 → 다시 열어 프로필 파일·화면이 같은지. 측정 중 읽기 전용은 기존 시험 |
| **B3** R2 Wi‑Fi 링크 근거 | `LinkCatalog.WlanState`/`WlanQuery`를 부르는 시험이 없고 Wi‑Fi 실측도 없다 | G2: 이벤트 ID → 상태 대응, 질의 문자열(시간 범위·채널), 유선과 같은 근거 경로로 합쳐지는지(가짜 기록 입력). Wi‑Fi 실측은 노트북에서 사용자 인수 항목으로 (N11과 함께 M12에서 다시 본다) |
| **B4** N14 첫 측정까지 단계 수 | 동의를 포함한 단계 수를 세는 게이트 시험이 없다 (M10에서 "동의 포함 세 단계 안"으로 정함) | G3: 동의 기록 없는 데모 실행에서 사용자 조작만 세어 측정 시작까지 3단계 이하(동의 → 시작)인지 |

### C. 전 화면 디자인 총점검

- **C1 빈 장면 채우기** (`m11-scenes.txt`, 형식은 m5와 같음):
  - 고대비(aquatic·desert)와 효과 줄이기(투명 효과 끔)가 하나도 없는 화면·대화상자: 첫 실행 5장면 중 대표 2, 프로필·프로필 TCP, 저장 안 한 변경 대화상자, DNS 비우기 확인, 기록 옮기기 확인, 기록 비교, 리포트 내보내기 상태.
  - 고대비 + 150% 조합: 화면마다 대표 1장면 (홈·측정·진단·기록·리포트·설정·사용 조건).
  - 설정 화면 진입·동의 → 셸 전환은 전환 프레임을 찍지 않았다: 기존 전환 프레임 장치로 각각 한 묶음.
- **C2 화면 위 대비 측정**: 지금은 홈·진단·기록·리포트·부품 전시만 실측한다. 측정·첫 실행·프로필·설정·사용 조건 화면에 같은 측정(유리 단계별 글자 대비, 다크·라이트)을 더한다. 기준은 M2 토큰 기준 그대로.
- **C3 시각 검토**: Claude가 최종 게이트 캡처 전부(약 700장)를 화면별 접촉 시트로 묶어 본다. 체크리스트(기획서 7절): 시안(D2)과 일치, 층·두께 규칙, 글자 가독성, 정렬·간격, 잘림, 초점 표시. 결과는 `M11-completion.md` "디자인 총점검" 절에 화면별 표로. Codex에는 접촉 시트를 이미지로 보내 G4에서 독립 평가를 받는다.
- **C4 미뤄 둔 재검토 3건** (판정만, 바꾸는 것은 사용자 확인 뒤):
  1. 흑요석 미세 결(M2 5.5): 시안과 나란히 비교해 "넣지 않음 유지 / 넣음" 판정. 넣는 것은 디자인 변경이라 사용자에게 묻는다.
  2. 콘텐츠를 제목 표시줄까지 넓히기(M5 4.2): 끌기·캡션 버튼·창 캡처·자동화 경계 위험이 그대로라 **넓히지 않음 유지**를 제안한다. 근거를 기록.
  3. 문구 점검(`Screens/Text.cs` 등 화면 문구 묶음): 기획서 7.5 원칙(결론 먼저, 쉬운 말, 단정하지 않음) 위반·맞춤법·용어 불일치를 목록으로. 고치는 것은 문구만이고 시험이 보는 문구는 시험과 함께 바꾼다.
- 결함이 나오면(잘림, 대비 부족, 초점 안 보임, 문구 오류) 그 화면만 고치고 해당 장면을 다시 찍는다.

### D. 맨 위 커밋에서 최종 증거

- **D1 최종 전체 게이트**: G4 승인 커밋 X에서 데스크톱 1회 — `build/build.ps1 -Gate` → (재부팅은 사용자 선택) → 사용자 클립보드 준비(`cmd /c "echo NetPulse| clip"`, 형식 이름만 확인) → `build/ui-test.ps1`. 그 앞의 중간 확인은 노트북 도구가 준비되면 노트북, 아니면 디버그 빌드의 해당 클래스만(사용자 허락 뒤).
- **D2 깨끗한 클론·CI**: `tools/loop/clean-clone.ps1 -Commit X`, 마감 스크립트의 PR CI.
- **D3 실측 시나리오 (게이트 밖, 공개 안 함)**: 최종 배포 exe(`artifacts/<X>/app/NetPulse.exe`)로 `Kind=Live` 시험 `M5LiveRunTests`~`M9LiveRunTests`를 돌린다. 출력은 `.loop/` 아래. 판정은 "앱이 관측한 것을 정확히 기록하고 보여주는가"(네트워크 성공은 판정 안 함). `M7LiveRunTests`는 실행 기록이 없어 처음 돈다. 풍선은 이미 사용자가 확인(M10), 이번에는 기록만.
- **D4 UI 시험의 CI 재검토 (M1 설계)**: 판정 제안 — **계속 CI에서 빼고 데스크톱 게이트로 둔다**. 근거: 834건 약 50분, 대화형 데스크톱·전경·클립보드·작업 표시줄이 필요, 노트북 실측에서 성능·타이밍 기준이 하드웨어에 따라 흔들렸다(825/834). M12의 게이트 단축과 함께 다시 볼 수 있다.

### E. 고침과 버전

- **E1 결함 처리**: 점검에서 나온 결함은 이 마일스톤에서 고친다(작은 것). 범위가 크면 사용자에게 M12로 옮길지 묻는다.
- **E2 버전**: 0.9.0을 유지한다. M11에서 제품 코드가 바뀌지 않으면 `5c30ef2`의 게시본이 그대로 유효하다는 것을 `M11-completion.md`에 남긴다(제품 소스 `src/` 차이 없음 + 같은 SDK). 제품 코드가 바뀌면 그 차이를 적고, 다시 게시할지(0.9.1)는 사용자에게 묻는다. exe 바이트는 커밋 해시가 박혀 늘 다르므로 "같은 제품"의 판단은 소스 차이로 한다.

### F. 인수 체크리스트 (`acceptance-checklist.md`)

항목마다: 무엇을, 어떻게(단계), 기대 결과, 기록 칸(날짜·결과·메모). 루프가 대신할 수 없는 것만 넣는다.

1. 실제 단선 실험 (공유기 전원·랜선을 뽑았다 꽂기): 끊김 판정·구간 후보·풍선
2. 장시간 측정 (예: 8시간 이상, 720분 한도 포함): 메모리·화면·기록 봉인
3. 화면 품질 (사용자가 직접 써 보며): 체감 지연, 깜빡임, 편안함
4. 실제 OS 고대비·투명 효과 끔·애니메이션 끔, 실제 DPI 150% (시험은 시뮬레이션)
5. 깨끗한 Windows 11 (가상 머신이나 다른 PC): 받기 → 실행 → 동의 → 측정
6. SmartScreen 경고와 실행
7. 트레이·풍선 (실제 작업 표시줄), 트레이 메뉴 [종료]
8. Wi‑Fi PC(노트북)에서 링크 근거 (R2 Wi‑Fi 경로)
9. 리포트를 통신사 제출용으로 열어 보기 (가린 값)
10. 법률 판단: 첫 실행 동의·원문 제공(Windows App SDK 3(b)(ii)), 배포자 면책 의무(3(b)(iii))
11. 알려진 문제: 금융 보안 프로그램이 있는 PC (M12에서 고침, 지금은 README 안내가 맞는지)

## 4. 상태표

| 위험 | 대응 |

| 새 장면으로 게이트 시간이 늘어남 | C1은 대표 장면만(약 40장 추가 예상). 늘어난 시간을 기록 |

| 실측 시나리오가 이 PC 네트워크 상태에 흔들림 | 통과 조건은 기록·표시의 정확성(기획서 4절). 결과는 `.loop/`에만 |

| 화면을 쓰는 작업이 사용자 PC 사용과 겹침 | 화면 작업은 묶어서 한 번에 허락받는다 |
