## 3. 설계

### A. 측정 끝 타임라인 선 빠짐 (C3 결함, STATE 미해결 지적 M11-3)

**원인 (코드와 캡처로 확인, 실제 화면 재현은 아직)**

- `MeasureScreen.RenderTimeline`은 `TimelineModel.Frame(..., columns: timeline.Columns, ...)`로 장면을 만든다. `TimelinePanel.Columns`는 `Math.Max(1, round(ActualWidth))`이므로, 배치 전(폭 0)에 부르면 **열 1개**로 계산된다.
- 열이 1개면 `TimelineModel.Series`는 모든 회차를 한 칸에 모아 칸 가운데에 최솟값~최댓값 점 하나를 둔다. 그래서 선 대신 그래프 가운데에 세로 막대 하나만 남는다. M11 `matrix-m5-measure-done-dark-100`이 정확히 이 모양이다. 인터넷 선은 x≈760(그래프 297~1222의 가운데)에 세로 막대로, 공유기 선은 아래쪽에 짧은 점선 조각으로 남는다.
- `TimelinePanel`의 `SizeChanged`는 **이미 받은 장면을 다시 그리기만** 한다(`Draw()`). 측정 화면은 폭이 바뀌어도 장면을 다시 계산하지 않는다.
- 측정 중이면 1초 뒤 다음 스냅숏이 오고, 그때 `drawKey`에 든 열 수가 달라 다시 계산되어 저절로 고쳐진다. **끝난 측정은 새 스냅숏이 없어** 열 1개 장면이 그대로 남는다.
- 매트릭스 장면 `measure-done`은 `--demo outage-long --demo-speed 600 --start`로 띄운다. 3분 계획이 1초도 안 되어 끝나므로, 측정 화면의 첫 배치 전에 끝나면 이 상태가 된다. 다크만·간헐인 이유는 시작 시점 차이로 추정한다(미확인). 고침은 이 이유에 기대지 않는다.
- 기록 화면은 이미 막혀 있다: 폭이 0이면 그리지 않고(`DrawTimelineNow`), 타임라인 `SizeChanged`에서 다시 계산한다(`QueueTimeline`). 홈의 "최근 2분" 타임라인도 배치 전에 계산할 수 있다. 하지만 `drawKey`가 없고 측정 중에만 그래프를 보이므로 다음 스냅숏(1초)에서 다시 계산된다. 끝난 측정처럼 남지는 않는다(Codex 확인). 같은 고침을 넣되 위험은 측정 화면보다 작다.

**실제 사용자 화면에 날 수 있는 경로 (재현 확인 필요)**

1. 측정 화면을 처음 여는 때가 측정이 끝난 뒤이고, 화면을 미리 만들어 배치해 두는 `ScreenHost.Prepare`가 아직 돌지 않은 경우. `Show`는 보이게 한 직후 같은 호출에서 `Render`를 부른다(배치 전).
2. 숨긴 화면이 돌아올 때 폭이 0으로 보고되는 경우 (WinUI에서 접힌 요소의 `ActualWidth`가 어떻게 되는지는 확인 필요).
3. 끝난 측정을 보는 중에 창 크기를 바꾸는 경우. 장면은 다시 계산되지 않고 옛 열 수로 늘려 그려진다(빠짐은 아니고 거칠어짐).

**고침**

- `TimelinePanel`이 마지막 장면을 만들 때 쓴 열 수를 기억한다. `SizeChanged`에서 지금 `Columns`가 그 값과 다르면 `ColumnsChanged` 이벤트를 낸다.
- 측정 화면·홈은 이 이벤트를 받으면 마지막 스냅숏으로 타임라인만 다시 그린다(`drawKey`에 열 수가 있으므로 다시 계산된다). 폭이 0이면 장면을 만들지 않고 `drawnKey`를 비워 둔다(기록 화면과 같은 규칙).
- 기록 화면도 같은 이벤트로 옮길지는 구현 때 본다(지금 동작은 맞다). 옮기면 동작 보존 시험을 그대로 돈다.
- 진단 값에 타임라인의 `frameColumns`와 `columns`(지금 폭)를 더한다.

**시험** [1-5]

- 우연한 재현에 기대지 않고 조건을 통제한다:
  - 시험 전용 옵션 `--test-finish-before-layout`을 둔다(시험 주입이 허용된 실행에서만).
  - 이 옵션은 데모 측정을 셸 창이 배치되기 전에 끝까지 돌린다. 그래서 측정 화면은 폭 0인 상태에서 끝난 스냅숏을 먼저 받는다.
  - 그 뒤 창을 배치하고, 스냅숏은 더 오지 않는다.
- 진단 값:
  - `hasFrame`
  - 지금 실제 폭 `width`
  - **장면 계산에 실제로 쓴 열 수** `frameColumns`
  - 첫 장면의 열 수 `firstFrameColumns` (조건이 실제로 만들어졌는지 확인용)
- 단언:
  - 조건 성립: `firstFrameColumns == 1`
  - 끝 상태: `hasFrame && width > 0 && frameColumns == round(width)`
- 고치기 전후 비교: 커밋을 둘로 나눈다.
  1. 진단 값·시험 옵션·시험만 넣은 커밋. 제품 동작은 그대로이고, 이 커밋의 exe에서 위 시험이 **실패**해야 한다.
  2. 고침 커밋. 같은 시험이 통과해야 한다.
  - 두 커밋의 exe를 노트북 중간 확인에서 같은 조건으로 돌리고, 결과를 DECISIONS에 적는다.
- 끝난 측정에서 창 크기를 바꾼 뒤 `frameColumns`가 새 폭을 따라가는지 본다.
- 안전망:
  - 매트릭스의 타임라인 장면(측정·홈·기록)에서 캡처 직전에 같은 단언을 둔다(`hasFrame`이면 `frameColumns == round(width)`).
  - G5: `measure-done` 다크·라이트 100%의 선 화소를 M11 C3 조건으로 센다(기록용).
- 실제 사용자 경로 1·2의 재현은 노트북 중간 확인에서 시도하고 결과를 적는다.

### B. 금융 보안 프로그램 충돌 (1.0.0 조건)

**아는 것 (DECISIONS "M10 SDK 고정과 공개 버전 0.9.0")**

- 노트북에서 NetPulse.exe가 시작 직후 0xc0000005로 끝났다. 오류 모듈은 RaonSecure TouchEn nxWeb의 `TENXWGuard64_102.dll`(다른 프로세스에 들어오는 DLL), 응용 프로그램 로그 Application Error 1000.
- TouchEn nxWeb·nxKey, KeySharp biz, nProtect Online Security, AhnLab Safe Transaction을 지우고 재부팅하자 정상 실행했다. 어느 프로그램 하나 때문인지는 가리지 않았다.

**모르는 것**: 앱의 어떤 동작(단일 파일 압축 풀기, Windows App SDK 초기화, 창·입력·네트워크 API 등)에서 그 DLL이 터지는지, 지금도 재현되는지, 앱 쪽에서 피할 수 있는지.

**순서**

1. **B0 (화면 안 씀, 지금 할 수 있음)**: 시작 경로 정리. `Main`부터 첫 창이 보일 때까지 앱이 부르는 것(단일 파일 번들 압축 풀기 위치, 네이티브 DLL 목록과 서명, Windows App SDK 부트스트랩, 키보드·입력 후킹 여부, 첫 네트워크 호출)을 문서로 적는다. 묶음에 든 네이티브 DLL마다 서명자를 적는다(아래 대응 후보 2의 전제).
2. **B1 재현 (노트북, 사용자 입회)**: 사용자가 해당 프로그램을 다시 설치한다(Claude는 설치·다운로드하지 않는다, 9절 질문 1). 0.9.0과 M12 후보 exe로 시작을 시도한다. 기록할 것: 응용 프로그램 로그의 오류 모듈·오프셋, WER 보고 폴더의 내용, 앱의 시작 단계 기록(아래 B2의 단계 기록이 어디까지 남았는지). 덤프 수집처럼 시스템 설정을 바꾸는 일은 사용자가 한다.
3. **B2 계측 (B1 전에 넣는다)** [1-6]
   - 관측할 수 없는 구간이 있다:
     - 단일 파일 번들 압축 풀기와 .NET 런타임 시작은 관리 코드보다 앞이라 앱이 기록할 수 없다.
     - 지금 앱 기록(`AppLog`)은 `App.Launch`에서야 만들어진다(`App` 생성·`InitializeComponent` 뒤).
   - 그래서 가장 이른 관리 코드 지점에서 작은 시작 기록 파일을 직접 연다.
     - 지점: 생성된 `Main` 대신 직접 둔 `Main`, 또는 `App` 생성자 첫 줄.
     - 실행마다 실행 ID를 둔다.
     - 단계: 관리 코드 진입, App 생성, 동의 확인, 창 생성, 첫 그리기, **시작 준비 완료**. 그리고 **정상 종료** 표시.
     - 단계 이름·시각·실행 ID만 쓴다(개인 정보 없음).
   - 해석 규칙:
     - 정상 종료 표시가 없는 실행만 "끊김"으로 본다.
     - 마지막 단계는 **도달 지점**일 뿐 충돌 지점이나 원인의 증명이 아니다.
     - 기록이 아예 없으면 관리 코드 전 실패다.
   - 기록이 없거나 원인을 가리지 못하면 WER 보고·덤프의 네이티브 스택과 로드된 모듈로 조사한다(덤프 설정은 사용자가 한다).
   - 같은 소스의 단일 파일 배포와 폴더 배포(압축 풀기 없음)를 비교하는 것도 조사 후보다.
   - WER 원본·덤프에는 개인 정보(경로·사용자 이름)가 들어 있다. 저장소에 넣지 않고 `.loop/` 아래에 두며, 공개 기록에는 요약만 적는다.
4. **B3 대응 (B1 결과로 정함)**: 후보.
   - 후보 1 — 원인 동작을 피한다: 특정 API·초기화 순서가 터지는 지점이면 그 동작을 바꾼다. 가장 좋지만 원인을 알아야 한다.
   - 후보 2 — 프로세스 완화 정책(Microsoft 서명 DLL만 로드): **사실상 쓸 수 없다.**
     - B0 조사(2026-11-22, 읽기 전용): 묶음 파일 459개 중 DLL은 234개다.
     - 서명이 있는 DLL은 230개다(Microsoft Corporation 55, .NET 174, Microsoft Windows 1).
     - 서명이 없는 4개는 앱 자신의 `NetPulse.dll`·`NetPulse.Core.dll`·`NetPulse.Design.dll`·`NetPulse.Platform.dll`이다. 압축 풀린 파일에서 로드되므로 정책이 앱 자신을 막을 가능성이 크다.
     - 프로세스 생성 때 이미 들어온 DLL은 막지 못한다.
     - 화면 읽기 프로그램·제3자 입력기처럼 DLL을 넣는 보조 기술을 막아 접근성을 해칠 수 있다.
     - 그래서 다른 근거가 나오지 않으면 쓰지 않는다.
   - 후보 3 — 안내: 직전 실행이 시작 단계에서 끊겼고 그 PC에 알려진 모듈이 있으면, 다음 실행에서 원인 가능성과 대처(해당 프로그램 업데이트·예외 등록·지우기)를 알린다. 고침이 아니라 안내다.
5. 1.0.0 조건의 판정 [1-3]
   - "고침"의 조건: 다음을 모두 지킨 실행에서 시작·측정·종료가 통과해야 한다.
     - **최종 후보 X의 실제 배포 설정 그대로** 실행한다(선택 옵션·환경 변수 없이).
     - 충돌이 재현된 같은 PC에서 한다.
     - 보안 프로그램을 **켠 채로** 한다.
   - 함께 남길 것:
     - 보안 프로그램 이름·버전·실행 중 여부(서비스·프로세스)
     - 그 실행에서 문제 모듈이 로드됐는지(로드된 모듈 목록)
     - 같은 PC에서 고치기 전 exe가 실패하는 것
   - 다음은 "고침"이 아니다: 보안 프로그램이 꺼져 있었거나 문제 모듈이 로드되지 않아 성공한 경우.
   - 선택 옵션을 켜야만 피해지면 "조건부 회피"로 적는다. 그것으로 1.0.0을 낼지는 사용자가 정한다(9절 질문 2).
   - 앱 쪽에서 피할 수 없을 때도 사용자가 정한다(9절 질문 2).

### C. N11 Wi‑Fi 신호 세기

기획서 N11: "신호 세기를 타임라인에 겹침. 무선 구간이 원인인지 가린다. 위치 권한 조건을 확인". M4·M9에서 이 PC가 유선이라 실측하지 못해 뺐고, 노트북 실측이 가능해져 다시 넣는다.

**읽기 (Platform)**

- **위치 권한** [1-2] (Microsoft 문서 두 개, Claude가 직접 확인, 2026-11-22):
  - "Wi‑Fi access and location" 문서가 위치 동의 없이 `ERROR_ACCESS_DENIED`를 준다고 적은 호출은 넷이다.
    - `WlanGetAvailableNetworkList`
    - `WlanGetNetworkBssList`
    - `WlanScan`
    - `WlanQueryInterface`의 `wlan_intf_opcode_current_connection`
  - 이 호출을 사용자 문맥에서 처음 부르면 앱마다 한 번 시스템 안내가 뜬다.
  - `WLAN_INTF_OPCODE` 문서는 `wlan_intf_opcode_realtime_connection_quality`가 위치에 민감한 정보를 빼서 위치 권한이 필요 없다고 적는다. 연결되지 않았으면 실패한다.
  - 최소 Windows 판은 두 문서 어디에도 없다(미리 보기 문서).
  - `wlan_intf_opcode_rssi`는 위 목록에 없지만, 권한이 필요 없다고 적혀 있지도 않다.
- **읽는 순서**:
  1. `WlanOpenHandle` → `WlanEnumInterfaces` → 측정 대상 어댑터(GUID로 대응)에 `wlan_intf_opcode_realtime_connection_quality`를 부른다. 링크 품질과 신호 값을 읽는다(구조체 필드는 구현 때 헤더·문서로 확인).
  2. OS나 드라이버가 그 opcode를 지원하지 않으면 `wlan_intf_opcode_rssi`(dBm)를 부른다. 이것이 위치 권한 없이 되는지는 노트북에서 확인한다.
  3. 둘 다 안 되면 상태는 "지원 안 함"이다.
- `wlan_intf_opcode_current_connection`과 목록·스캔 호출은 **부르지 않는다.** 위치 안내를 띄우지 않기 위해서다. 필요한 값(품질·신호)은 위 1·2로 얻는다.
- 접근 거부가 오면 "권한 없음"으로 기록하고 측정은 계속한다. 빠지는 것은 신호뿐이다.
- 앱은 시스템 설정을 바꾸지 않는다.
- 1·2만 쓰므로 위치 안내는 뜨지 않을 것으로 본다. 실제로 안 뜨는지는 노트북에서 확인해 적는다.
- 상태는 기존 링크 근거와 같은 원칙: 지원 안 함·권한 없음·값 없음·관측을 정상으로 보지 않는다.
- **개인 정보**: SSID·BSSID는 읽더라도 기록·화면·리포트에 넣지 않는다. 기록하는 것은 어댑터(기존 식별 방식)·신호 품질·RSSI·상태뿐이다.

**기록 (Core)**

- **표본과 기록의 계약** [1-4]
  - 읽기:
    - 측정 회차와 같은 주기로 읽는다. 측정 엔진 쓰기 경로 밖, 링크 수집과 같은 쪽에서 읽는다.
    - 표본 하나는 (시각, 어댑터, 상태, 품질 0~100 또는 없음, RSSI 또는 없음)이다.
    - 품질 0%는 값이다. "값 없음"과 다르다.
  - 기록:
    - 값이나 상태가 바뀔 때 `signal` 이벤트를 쓴다.
    - 그 값은 **다음 이벤트 또는 그 어댑터의 마지막 표본 시각까지** 유효하다.
    - 반복 표본은 줄로 쓰지 않는다. 대신 60초마다 체크포인트 이벤트에 마지막 표본 시각과 그때까지의 표본 수를 쓴다.
    - 끝 요약이 없는 기록(비정상 종료)도 마지막 체크포인트·이벤트까지는 복원된다. 잃는 것은 최대 60초이고, 화면·리포트에는 "마지막 관측"으로 표시한다.
  - 평균:
    - **유효 구간의 시간 가중 평균**이다. 같은 값이 유지된 시간만큼 센다.
    - 표본이 주기적이므로 표본 평균과 같다(예: 80%가 99초, 20%가 1초면 79.4%).
  - 끝 요약:
    - 어댑터별 표본 수, 시간 가중 평균, 최저, 상태별 시간을 넣는다.
    - 읽을 때 요약이 있으면 요약을, 없으면 이벤트로 다시 계산한다. 두 값이 같은지 시험한다.
  - 선을 끊는 경우는 셋이다. 끊긴 구간은 평균에 넣지 않는다.
    - 상태가 정상이 아님: 권한 없음, 지원 안 함, 연결 안 됨, 읽기 실패
    - 측정 공백: 절전, 멈춤 (기존 공백 규칙)
    - 어댑터가 바뀜
  - 실시간 화면은 이벤트가 아니라 실시간 사본에서 마지막 표본까지 그린다. 지금 링크의 `LinkLive`와 같은 방식이다.
- **기록 형식 호환**:
  - Codex 확인: `RecordReader.ParseEvent`는 모르는 종류의 이벤트도 공통 필드가 맞으면 **보존**하고, 소비자가 필요한 종류를 고른다.
  - 두 방향을 나눠 확인한다.
    - 새 읽기가 옛 기록(신호 없음)을 읽는다.
    - 옛 0.9.0 읽기가 새 기록을 읽을 때 손상 판정이 늘지 않는다.
  - 여러 조각으로 나뉜 기록에서도 복원 시험을 둔다.
- 데모: 신호 값을 내는 데모 시나리오(약해졌다 끊김, 강한데 끊김)를 더한다.

**표시**

- 측정·기록 화면 타임라인 [1-7]: 무선 어댑터가 관측된 측정에만 신호 품질 선을 겹친다.
  - 그래프 영역:
    - 오른쪽 축 글("100%"·"0%")을 위한 여백을 뺀다.
    - 시간축·선·띠·끝 시각을 모두 남은 같은 영역에 둔다. 지금은 전체 폭이 시간축이다.
    - 신호가 없는 측정은 여백 없이 지금과 같다.
  - 어댑터:
    - 측정의 기본 경로 어댑터 하나의 선만 그린다.
    - 경로 어댑터가 바뀌면 선을 끊고 새 어댑터로 잇는다. 바뀐 시각은 위쪽 표시 줄에 표시한다.
    - 다른 무선 어댑터는 범례·리포트에 이름 없이 수만 적는다.
    - 그래서 선은 언제나 많아야 하나이고, 성능 전제(간추리기 열 수 × 2)가 그대로다.
  - 색·모양:
    - 지연 선과 다른 색·점 모양을 쓴다.
    - 그래프 배경과의 대비는 3:1 이상이다(기획서 그래프 기준).
    - 고대비에서는 시스템 색을 쓴다.
    - 범례에 더한다.
  - 권한 없음·지원 안 함이면 선 대신 범례 자리에 상태를 적는다.
  - 검사 장면: 100%·150%, 다크·라이트·고대비, 긴 상태 문구, 어댑터 바뀜. 축 글·끝 시각·범례가 겹치지 않는지 배치 검사로 본다.
- 리포트: 무선 어댑터 줄에 신호 평균·최저와 상태. 원인 단정은 하지 않는다("끊김 동안 신호가 낮았다"처럼 관측만).
- 분석 판정(`Verdict`·후보)은 1.0.0에서 바꾸지 않는다. 신호는 근거 표시로만 쓴다.

**시험**: Platform 해석 시험(가짜 API 결과 → 상태·값), Core 기록 왕복·모르는 이벤트 무시·요약, 타임라인 모델 시험, 데모 장면 캡처(측정·기록·리포트), 노트북 실측은 인수 항목.

### E. 흑요석 미세 결

- `M11-completion.md` 2절 재검토 1의 방향: 배경 빛 층 위에 고정 점 결 이미지 한 층(토큰 불투명도). 결 이미지는 코드로 만든 결정적 잡음(시드 고정)을 앱 자원으로 넣는다(외부 그림 없음, 고지 대상 아님).
- 다크·라이트 각각 불투명도 토큰. 투명 효과 끔·고대비에서는 끈다.
- 판단: 시안과 같은 자리를 나란히 놓은 비교 이미지로 눈으로 본다.
- M11의 밝기 표준편차는 빛 번짐까지 섞인 값이다. **참고 수치로만** 적고 합격선으로 쓰지 않는다.
- 본문 대비가 떨어지지 않는지는 F의 실측으로 본다.
- 투명 효과 끔 면 색(다크 자줏빛·라이트 베이지로 물듦)은 흑요석 기준색에서 다시 만든다.
- 성능: 결 층은 정적 이미지 한 장이라 전환·idle 예산에 영향이 없어야 한다. M2 전환 bench로 확인.

### F. 화면 대비 실측 확장

- 대상: 강조 단추·유리 단추 글, `StatusChip`·`ScreenParts.InfoChip`(라벨·값), 배너(종류별), 카드 본문 글(작은 글이 없는 카드 포함, 예: `measure.timeline.range`), 비활성 단추(기준은 비활성 예외 여부를 9절 질문 3으로).
- 방식은 M11과 같다: `--hide-measured-text`에서 그 글만 투명하게 한 캡처와 원래 캡처의 차로 글 화소·배경을 얻는다. 부품마다 숨김 고리와 필수 자동화 ID를 단다.
- `M11ContrastTests.Required`에 장면별 필수 요소를 더하고, 빠지면 실패. 기준 4.5:1(큰 글 3:1).
- M11 G4 3라운드 사소: 대비 시험 주석의 두 칩 구성을 나눠 적는다.

### G. 게이트·시험

**G1 시간 단축** (M10 기록: UI 834건 49.5분, 매트릭스 58%)

- C(운영): 이미 적용. 라운드 중 노트북 부분·전체 확인, 최종 X에서 데스크톱 전체 1회.
- B [1-1]: 매트릭스 캡처 전 고정 대기 `Thread.Sleep(700)`(M5·M10·M11 매트릭스, G5·M5G5)을 **상태 기반 대기**로 바꾼다. 화소 안정은 보조 조건이다.
  - 왜 화소만으로는 안 되는가:
    - `--freeze-motion`은 반복 모션만 막는다(`Motion.Frozen`).
    - 등장·페이드·차례 등장 지연처럼 한 번 도는 모션은 그대로 돈다.
    - 기록 타임라인은 프레임·낮은 우선순위 큐를 거쳐 그린다.
    - 그래서 화소가 두 번 같아도 아직 그리기 전이거나 지연 중일 수 있다.
  - 앱 진단 값에 "그리기 끝남" 조건을 더한다:
    - 진행 중인 한 번 도는 모션 수 0
    - 대기 중인 화면 그리기 큐 0 (기록 타임라인 포함)
    - 타임라인 `hasFrame`과 A의 열 수 일치
    - 지금 화면의 필수 요소 배치 완료
  - 시험은 다음 순서로 기다린다:
    1. 장면의 기대 상태 (기존 `wait:`)
    2. 위 "그리기 끝남"
    3. 창 캡처 두 번이 같음 (보조)
  - 최대 대기는 지금과 같은 700 ms다. 넘으면 기존처럼 찍는다.
  - 결과에는 `settled`(1~3 충족)와 `timedOut`을 나눠 기록한다.
  - 진행도를 고정한 전환 장면(`--motion-hold`)은 2의 모션 조건에서 뺀다. 일부러 멈춘 모션이기 때문이다.
  - 첫 실행에서 M11 캡처와 장면별로 비교한다.
  - 빨라졌는지는 실측으로만 말한다. 캡처가 늘어 느려질 수도 있다.
- A: 매트릭스만 2개 병렬. 위험: 전경·초점을 다투는 장면(초점 테두리, 키보드)과 PC 부하. B 결과를 본 뒤, 초점이 필요 없는 장면만 병렬로 돌리는 안을 따로 판단한다(A는 이번에 안 할 수도 있음, 근거를 남긴다).
- 증거: 같은 PC에서 단축 전후 전체 UI 시험 시간.

**G2 프레임 기준의 주사율 전제**

- 지금 idle 95백분위 ≤ 16.7 ms(`MotionTokens.IdleP95`)는 60 Hz 화면에서 간격 자체가 16.7 ms라 구조적으로 넘기 쉽다(노트북 16.93 ms).
- 안:
  - 시험 시작 때 **앱 창이 있는 모니터**의 주사율을 읽는다(출처: 그 모니터의 표시 설정 값).
  - g5 결과에 주사율과 그 출처를 기록한다.
  - 기준은 `max(16.7 ms, 1.25 × 주사 간격)`이다. 60 Hz는 20.8 ms, 165 Hz는 16.7 ms(지금과 같음).
  - idle 판정 두 곳(G5 idle, M5G5)에 똑같이 쓴다.
  - 전환 최대 50 ms 기준은 그대로다.
- 한계 (결과에 적는다):
  - 재는 것은 렌더링 콜백 간격이다. 실제 화면에 나간 프레임이 아니다.
  - 가변 주사율 화면에서 읽은 값은 최대 주사율이다.
- 대안: "놓친 프레임 비율"(간격이 주사 간격의 1.5배를 넘은 프레임 비율)로 바꾸기. 계측을 바꿔야 해서 이번에는 1안을 추천한다.

**G3 시간 민감 시험** (STATE 미해결 지적 M11-5)

- 먼저 CI 기록으로 제품 쪽 관측 지연이 비정상인지 본다.

## 7. 위험

- **B가 재현되지 않거나 앱 쪽에서 못 고침**: 1.0.0 조건을 채우지 못한다. 사용자 결정으로 넘긴다(9절).
- **B 후보 2**: 앱 자신의 서명 없는 DLL을 막을 가능성이 크고, 보조 기술·입력기도 막을 수 있다. 쓰지 않는다.
- **C 지원 범위**: OS·드라이버가 위치 권한 없는 품질 조회를 지원하지 않고 RSSI까지 막히면, 많은 사용자에게 "지원 안 함"만 보일 수 있다. 노트북 결과로 기능 가치를 사용자와 다시 본다.
- **C 기록 형식**: 새 이벤트가 옛 읽기에서 오류를 내면 0.9.0 사용자의 기록 열기에 영향. 모르는 이벤트 무시를 시험으로 고정한다.
- **D 문구 변경 범위가 넓음**: 시험 기대 문구 수정이 많다. 문구 하나를 바꿀 때 그 문구를 단언하는 시험을 함께 찾는다(grep).
- **G1-B 대기 축소로 캡처가 덜 그려진 상태**: 상태 기반 대기가 먼저이고 화소 안정은 보조다. 배치 검사는 Canvas 안의 선 누락을 잡지 못한다(M11 결함도 통과했다). 그래서 A의 열 수 단언을 함께 둔다. 첫 실행에서 M11 캡처와 장면별로 비교한다.
- **화면 확인이 노트북·사용자 일정에 묶임**: 1~3단계를 먼저 끝내 두고, 4단계부터 한꺼번에 확인한다.
