1판 · 2026-11-22 · 브랜치 `loop/m12-release` (`main` `32ac9d1` = M11 병합 위)

## 3. 설계

### A. 측정 끝 타임라인 선 빠짐 (C3 결함, STATE 미해결 지적 M11-3)

**원인 (코드와 캡처로 확인, 실제 화면 재현은 아직)**

- `MeasureScreen.RenderTimeline`은 `TimelineModel.Frame(..., columns: timeline.Columns, ...)`로 장면을 만든다. `TimelinePanel.Columns`는 `Math.Max(1, round(ActualWidth))`이므로, 배치 전(폭 0)에 부르면 **열 1개**로 계산된다.
- 열이 1개면 `TimelineModel.Series`는 모든 회차를 한 칸에 모아 칸 가운데에 최솟값~최댓값 점 하나를 둔다. 그래서 선 대신 그래프 가운데에 세로 막대 하나만 남는다. M11 `matrix-m5-measure-done-dark-100`이 정확히 이 모양이다. 인터넷 선은 x≈760(그래프 297~1222의 가운데)에 세로 막대로, 공유기 선은 아래쪽에 짧은 점선 조각으로 남는다.
- `TimelinePanel`의 `SizeChanged`는 **이미 받은 장면을 다시 그리기만** 한다(`Draw()`). 측정 화면은 폭이 바뀌어도 장면을 다시 계산하지 않는다.
- 측정 중이면 1초 뒤 다음 스냅숏이 오고, 그때 `drawKey`에 든 열 수가 달라 다시 계산되어 저절로 고쳐진다. **끝난 측정은 새 스냅숏이 없어** 열 1개 장면이 그대로 남는다.
- 매트릭스 장면 `measure-done`은 `--demo outage-long --demo-speed 600 --start`로 띄운다. 3분 계획이 1초도 안 되어 끝나므로, 측정 화면의 첫 배치 전에 끝나면 이 상태가 된다. 다크만·간헐인 이유는 시작 시점 차이로 추정한다(미확인). 고침은 이 이유에 기대지 않는다.
- 기록 화면은 이미 막혀 있다: 폭이 0이면 그리지 않고(`DrawTimelineNow`), 타임라인 `SizeChanged`에서 다시 계산한다(`QueueTimeline`). 홈의 "최근 2분" 타임라인은 측정 화면과 같은 모양이라 같은 위험이 있다.

**실제 사용자 화면에 날 수 있는 경로 (재현 확인 필요)**

1. 측정 화면을 처음 여는 때가 측정이 끝난 뒤이고, 화면을 미리 만들어 배치해 두는 `ScreenHost.Prepare`가 아직 돌지 않은 경우. `Show`는 보이게 한 직후 같은 호출에서 `Render`를 부른다(배치 전).
2. 숨긴 화면이 돌아올 때 폭이 0으로 보고되는 경우 (WinUI에서 접힌 요소의 `ActualWidth`가 어떻게 되는지는 확인 필요).
3. 끝난 측정을 보는 중에 창 크기를 바꾸는 경우. 장면은 다시 계산되지 않고 옛 열 수로 늘려 그려진다(빠짐은 아니고 거칠어짐).

**고침**

- `TimelinePanel`이 마지막 장면을 만들 때 쓴 열 수를 기억한다. `SizeChanged`에서 지금 `Columns`가 그 값과 다르면 `ColumnsChanged` 이벤트를 낸다.
- 측정 화면·홈은 이 이벤트를 받으면 마지막 스냅숏으로 타임라인만 다시 그린다(`drawKey`에 열 수가 있으므로 다시 계산된다). 폭이 0이면 장면을 만들지 않고 `drawnKey`를 비워 둔다(기록 화면과 같은 규칙).
- 기록 화면도 같은 이벤트로 옮길지는 구현 때 본다(지금 동작은 맞다). 옮기면 동작 보존 시험을 그대로 돈다.
- 진단 값에 타임라인의 `frameColumns`와 `columns`(지금 폭)를 더한다.

**시험**

- G3: 매트릭스의 타임라인이 있는 장면(측정·홈·기록)에서 캡처 직전 `frameColumns == columns`를 단언한다. 이 단언은 고치기 전 코드의 `measure-done`에서 실패해야 한다(노트북 중간 확인에서 먼저 실패를 본다).
- G3: 끝난 측정에서 창 크기를 바꾼 뒤 `frameColumns`가 새 폭을 따라가는지.
- G5: `measure-done` 다크·라이트 100%의 선 화소를 M11 C3과 같은 조건으로 센다(기록용, 단언 아님).
- 경로 1·2의 실제 재현은 노트북 중간 확인에서 시도하고 결과를 DECISIONS에 적는다. 재현이 안 돼도 고침은 넣는다(재현 없음 = 해결 아님 원칙의 반대 방향, 위험이 작고 코드가 원인을 직접 막음).

### B. 금융 보안 프로그램 충돌 (1.0.0 조건)

**아는 것 (DECISIONS "M10 SDK 고정과 공개 버전 0.9.0")**

- 노트북에서 NetPulse.exe가 시작 직후 0xc0000005로 끝났다. 오류 모듈은 RaonSecure TouchEn nxWeb의 `TENXWGuard64_102.dll`(다른 프로세스에 들어오는 DLL), 응용 프로그램 로그 Application Error 1000.
- TouchEn nxWeb·nxKey, KeySharp biz, nProtect Online Security, AhnLab Safe Transaction을 지우고 재부팅하자 정상 실행했다. 어느 프로그램 하나 때문인지는 가리지 않았다.

**모르는 것**: 앱의 어떤 동작(단일 파일 압축 풀기, Windows App SDK 초기화, 창·입력·네트워크 API 등)에서 그 DLL이 터지는지, 지금도 재현되는지, 앱 쪽에서 피할 수 있는지.

**순서**

1. **B0 (화면 안 씀, 지금 할 수 있음)**: 시작 경로 정리. `Main`부터 첫 창이 보일 때까지 앱이 부르는 것(단일 파일 번들 압축 풀기 위치, 네이티브 DLL 목록과 서명, Windows App SDK 부트스트랩, 키보드·입력 후킹 여부, 첫 네트워크 호출)을 문서로 적는다. 묶음에 든 네이티브 DLL마다 서명자를 적는다(아래 대응 후보 2의 전제).
2. **B1 재현 (노트북, 사용자 입회)**: 사용자가 해당 프로그램을 다시 설치한다(Claude는 설치·다운로드하지 않는다, 9절 질문 1). 0.9.0과 M12 후보 exe로 시작을 시도한다. 기록할 것: 응용 프로그램 로그의 오류 모듈·오프셋, WER 보고 폴더의 내용, 앱의 시작 단계 기록(아래 B2의 단계 기록이 어디까지 남았는지). 덤프 수집처럼 시스템 설정을 바꾸는 일은 사용자가 한다.
3. **B2 계측 (B1 전에 넣는다)**: 앱 시작 단계를 앱 기록 폴더에 한 줄씩 남긴다(번들 풀기 뒤, 런타임 시작, App 생성, 창 생성, 첫 그리기, 측정 엔진 시작). 다음 실행에서 앞 실행이 어느 단계에서 끊겼는지 읽을 수 있다. 개인 정보는 넣지 않는다(단계 이름과 시각만).
4. **B3 대응 (B1 결과로 정함)**: 후보.
   - 후보 1 — 원인 동작을 피한다: 특정 API·초기화 순서가 터지는 지점이면 그 동작을 바꾼다. 가장 좋지만 원인을 알아야 한다.
   - 후보 2 — 프로세스 완화 정책: 시작 직후 `SetProcessMitigationPolicy`로 Microsoft 서명이 아닌 DLL의 이후 로드를 막는다. 위험: 프로세스 생성 때 이미 들어온 DLL은 못 막는다. 앱 자신의 네이티브 DLL이 Microsoft 서명이 아니면 앱이 깨진다(B0 목록). 화면 읽기 프로그램·제3자 입력기처럼 DLL을 넣는 보조 기술을 막아 **접근성을 해칠 수 있다.** 그래서 기본으로 켜지 않고, 재현에서 효과와 부작용을 확인한 뒤에만 고려한다.
   - 후보 3 — 안내: 직전 실행이 시작 단계에서 끊겼고 그 PC에 알려진 모듈이 있으면, 다음 실행에서 원인 가능성과 대처(해당 프로그램 업데이트·예외 등록·지우기)를 알린다. 고침이 아니라 안내다.
5. 1.0.0 조건의 판정: 후보 1 또는 2로 같은 PC에서 시작·측정·종료가 통과하면 "고침". 앱 쪽에서 피할 수 없으면 후보 3과 README 안내로 1.0.0을 낼지는 사용자 결정이다(9절 질문 2).

### C. N11 Wi‑Fi 신호 세기

기획서 N11: "신호 세기를 타임라인에 겹침. 무선 구간이 원인인지 가린다. 위치 권한 조건을 확인". M4·M9에서 이 PC가 유선이라 실측하지 못해 뺐고, 노트북 실측이 가능해져 다시 넣는다.

**읽기 (Platform)**

- Native Wi‑Fi API: `WlanOpenHandle` → `WlanEnumInterfaces` → 측정 대상 어댑터(GUID로 대응)에 `WlanQueryInterface(wlan_intf_opcode_current_connection)`의 `wlanSignalQuality`(0~100)와, 되면 `wlan_intf_opcode_rssi`(dBm).
- **위치 권한**: 최근 Windows는 일부 무선 API에 위치 권한을 요구한다. 어떤 호출이 막히는지(SSID가 든 연결 정보만인지, 신호 값도인지), 막히면 어떤 오류로 오는지는 **노트북에서 확인한다**(지금은 추정). 앱은 시스템 설정을 바꾸지 않는다. 막히면 상태를 "권한 없음"으로 기록하고 화면에 알린다. 설정 열기 단추(`ms-settings:privacy-location`)는 F7의 설정 열기와 같은 방식으로 둔다.
- 상태는 기존 링크 근거와 같은 원칙: 지원 안 함·권한 없음·값 없음·관측을 정상으로 보지 않는다.
- **개인 정보**: SSID·BSSID는 읽더라도 기록·화면·리포트에 넣지 않는다. 기록하는 것은 어댑터(기존 식별 방식)·신호 품질·RSSI·상태뿐이다.

**기록 (Core)**

- 측정 회차와 같은 주기로 읽되, 값이 바뀔 때만 기록 이벤트(`signal`)를 쓴다(링크 반복 표본과 같은 방식). 끝 요약에 무선 어댑터별 표본 수·평균·최저를 넣는다.
- 기록 형식: 새 이벤트 종류를 더한다. 기존 읽기가 모르는 이벤트 종류를 건너뛰는지 확인하고 시험으로 고정한다. 0.9.0이 1.0.0 기록을 열 때 신호만 빠지고 나머지가 보이는지도 본다(하위 호환은 요구가 아니라 확인).
- 데모: 신호 값을 내는 데모 시나리오(약해졌다 끊김, 강한데 끊김)를 더한다.

**표시**

- 측정·기록 화면 타임라인: 무선 어댑터가 관측된 측정에만 신호 품질 선을 오른쪽 축(0~100%)으로 겹친다. 색·선 모양은 지연 선과 다르게 하고 범례에 더한다. 권한 없음·지원 안 함이면 선 대신 범례 자리에 상태를 적는다.
- 리포트: 무선 어댑터 줄에 신호 평균·최저와 상태. 원인 단정은 하지 않는다("끊김 동안 신호가 낮았다"처럼 관측만).
- 분석 판정(`Verdict`·후보)은 1.0.0에서 바꾸지 않는다. 신호는 근거 표시로만 쓴다.

**시험**: Platform 해석 시험(가짜 API 결과 → 상태·값), Core 기록 왕복·모르는 이벤트 무시·요약, 타임라인 모델 시험, 데모 장면 캡처(측정·기록·리포트), 노트북 실측은 인수 항목.

### D. 문구 중간·낮음과 C3 표시 결함

### E. 흑요석 미세 결

- `M11-completion.md` 2절 재검토 1의 방향: 배경 빛 층 위에 고정 점 결 이미지 한 층(토큰 불투명도). 결 이미지는 코드로 만든 결정적 잡음(시드 고정)을 앱 자원으로 넣는다(외부 그림 없음, 고지 대상 아님).
- 다크·라이트 각각 불투명도 토큰. 투명 효과 끔·고대비에서는 끈다.
- 수치 목표: 시안과 같은 자리의 밝기 표준편차가 시안에 가깝게 (M11 측정 방법 그대로). 본문 대비가 떨어지지 않는지 F의 실측으로 본다.
- 투명 효과 끔 면 색(다크 자줏빛·라이트 베이지로 물듦)은 흑요석 기준색에서 다시 만든다.
- 성능: 결 층은 정적 이미지 한 장이라 전환·idle 예산에 영향이 없어야 한다. M2 전환 bench로 확인.

### F. 화면 대비 실측 확장

- 대상: 강조 단추·유리 단추 글, `StatusChip`·`ScreenParts.InfoChip`(라벨·값), 배너(종류별), 카드 본문 글(작은 글이 없는 카드 포함, 예: `measure.timeline.range`), 비활성 단추(기준은 비활성 예외 여부를 9절 질문 3으로).
- 방식은 M11과 같다: `--hide-measured-text`에서 그 글만 투명하게 한 캡처와 원래 캡처의 차로 글 화소·배경을 얻는다. 부품마다 숨김 고리와 필수 자동화 ID를 단다.
- `M11ContrastTests.Required`에 장면별 필수 요소를 더하고, 빠지면 실패. 기준 4.5:1(큰 글 3:1).
- M11 G4 3라운드 사소: 대비 시험 주석의 두 칩 구성을 나눠 적는다.
- 순서: D·E 뒤에 잰다(문구·결이 바뀌면 다시 재야 하므로).

### G. 게이트·시험

**G1 시간 단축** (M10 기록: UI 834건 49.5분, 매트릭스 58%)

- C(운영): 이미 적용. 라운드 중 노트북 부분·전체 확인, 최종 X에서 데스크톱 전체 1회.
- B: 매트릭스 캡처 전 고정 대기 `Thread.Sleep(700)`(M5·M10·M11 매트릭스, G5·M5G5)을 **그리기 안정 대기**로 바꾼다. 창만 캡처(PrintWindow)를 짧은 간격으로 두 번 연속 같을 때까지(최소 1회 간격, 최대 700 ms). 모션은 `--freeze-motion`으로 이미 멈춘다. 캐럿 깜빡임처럼 계속 바뀌는 장면은 최대 대기로 끝나므로 지금보다 느려지지 않는다.
- A: 매트릭스만 2개 병렬. 위험: 전경·초점을 다투는 장면(초점 테두리, 키보드)과 PC 부하. B 결과를 본 뒤, 초점이 필요 없는 장면만 병렬로 돌리는 안을 따로 판단한다(A는 이번에 안 할 수도 있음, 근거를 남긴다).
- 증거: 같은 PC에서 단축 전후 전체 UI 시험 시간.

**G2 프레임 기준의 주사율 전제**

- 지금 idle 95백분위 ≤ 16.7 ms(`MotionTokens.IdleP95`)는 60 Hz 화면에서 간격 자체가 16.7 ms라 구조적으로 넘기 쉽다(노트북 16.93 ms).
- 안: 시험 시작 때 화면 주사율을 읽어 g5 결과에 기록하고, 기준을 `max(16.7 ms, 1.25 × 주사 간격)`으로 한다. 60 Hz는 20.8 ms, 165 Hz는 16.7 ms(지금과 같음). 전환 최대 50 ms 기준은 그대로.
- 대안: "놓친 프레임 비율"(간격이 주사 간격의 1.5배를 넘은 프레임 비율)로 바꾸기. 계측을 바꿔야 해서 이번에는 1안을 추천한다.

**G3 시간 민감 시험** (STATE 미해결 지적 M11-5)

- `SessionLinkTests.LiveLinkStateCarriesAnOngoingDownIntoTheProvisionalAnalysis`: 80회차를 연달아 넘긴 뒤 관측을 기다리다 CI에서 시간 초과. `Rounds`가 몇 회차마다 관측을 기다리게 하거나, 이 시험만 넉넉한 대기(`EventuallyWithin`)를 쓴다. 제품 쪽 관측 지연이 비정상인지 먼저 CI 기록으로 본다.

## 7. 위험

- **B가 재현되지 않거나 앱 쪽에서 못 고침**: 1.0.0 조건을 채우지 못한다. 사용자 결정으로 넘긴다(9절).
- **B 후보 2의 부작용**: 보조 기술·입력기 차단. 기본으로 켜지 않는다.
- **C 위치 권한**: 신호 값까지 막히면 대부분의 사용자에게 "권한 없음"만 보일 수 있다. 이 경우 기능 가치를 사용자와 다시 본다.
- **C 기록 형식**: 새 이벤트가 옛 읽기에서 오류를 내면 0.9.0 사용자의 기록 열기에 영향. 모르는 이벤트 무시를 시험으로 고정한다.
- **D 문구 변경 범위가 넓음**: 시험 기대 문구 수정이 많다. 문구 하나를 바꿀 때 그 문구를 단언하는 시험을 함께 찾는다(grep).
- **G1-B 대기 축소로 캡처가 덜 그려진 상태**: 두 번 연속 같음 조건과 기존 배치 검사로 막는다. 첫 실행에서 M11 캡처와 장면별로 비교한다.
- **화면 확인이 노트북·사용자 일정에 묶임**: 1~3단계를 먼저 끝내 두고, 4단계부터 한꺼번에 확인한다.
