## 2026-11-13 · M0 스파이크 합격선 (측정 전에 정함)

두 후보(A: WebView2 웹 화면 + .NET 본체, C: WinUI 3)에 같은 시험 장면을 만든다.

**시험 장면**: 1280×800 창, 배율 100%. 흐르는 배경 빛, 매초 새 값이 들어오며 부드럽게 흘러가는 3계열 실시간 그래프, 그 위에 겹친 유리 패널 3장(그중 둘은 두 단으로 겹침), 화면 전환 1종, 테마 전환.

- P1~P8 중 하나라도 못 넘으면 그 후보는 불합격이다. 둘 다 합격하면 표현력(굴절·광택·모션의 자유도), 배포 크기, 구현 난이도를 비교해 추천한다.
- 창 뒤 바탕화면 비침(Mica, Desktop Acrylic)은 가산점이고 합격 조건이 아니다.

**이 PC에서 하지 않는 것**

- Windows의 투명 효과, 애니메이션, 고대비, 배율 설정을 바꾸지 않는다. 사용자 시스템 설정이기 때문이다. P9는 설정을 읽는 것과 앱의 강제 옵션으로 대신한다. 실제 설정 변경 시험은 사용자 인수 항목이다.
- 한글 입력은 자동화가 보내는 유니코드 문자 입력만 확인한다. 입력기 조합 과정은 사용자 인수 항목이다.
- 프레임 수치는 이 PC 한 대의 값이다.

## 2026-11-13 · 스파이크 진행 중 발견

- **측정 루프 버그 (공용 코드, 수정함)**: 타이머가 예정보다 일찍 깨면 같은 회차를 두 번 기록했다(48초에 56회차). 일찍 깨면 다시 기다리게 고쳤다. 제품 엔진(M3)의 테스트 항목으로 넘긴다.
- **A안 메모리**: WebView2가 프로세스 7개를 띄워 작업 집합 합계가 합격선(400 MB)을 넘었다. 합격선은 바꾸지 않는다. 프로세스 사이 공유 페이지를 빼고 센 전용 작업 집합을 보조 지표로만 함께 기록한다.
- **C안 시작 직후 종료 (내 버그, 수정함)**: 측정 루프의 첫 회차가 화면 배치보다 먼저 도착하면 그래프 갱신에서 null 참조가 났고, 그 예외가 `CoreMessagingXP.dll`의 예외(0xc000027b)로 앱을 종료시켰다. 실행 속도에 따라 들쭉날쭉했다. 1차 예외를 기록해 찾았다.
  - **정정**: 이 버그를 모른 채 한때 "단일 파일 배포를 켜면 종료된다", "폴더 배포에 파일이 빠져 종료된다"고 적었다. 버그를 고친 뒤 단일 파일 배포본(`EnableMsixTooling` 필요)을 세 번 실행해 모두 정상이었다. 두 결론은 틀렸고 지운다.
  - 교훈(제품에 적용): 화면이 준비되기 전에 측정 결과가 도착하는 경우를 처리해야 한다. A안은 화면 준비 신호(`ready`) 전에는 보내지 않게 되어 있었다.
- **C안 폴더 배포의 파일 누락**: 단일 파일이 아닌 폴더 배포에서 `App.xbf`와 앱 `.pri`가 배포 폴더에 복사되지 않는 것은 관측했다. 이것이 실행에 문제가 되는지는 확인하지 않았다. 배포 뒤 복사하는 빌드 단계를 넣어 두었다.
- **C안 원형 테마 확산 미구현**: Composition 클립 애니메이션이 필요해 스파이크에서는 짧은 교차 페이드로 대신했다. 구현 가능성은 확인하지 않았다.
- **A안 창 뒤 재질(가산점)**: Mica 설정 호출은 성공(반환 0)했지만 웹 화면 바탕이 불투명해 보이지 않는다. 투명 바탕과의 조합은 시험하지 않았다.

## 2026-11-13 · D2 디자인 방향: 흑요석 (사용자 결정)

- 사용자 답: 오로라와 흑요석이 둘 다 좋다. 흑요석은 깔끔해서, 오로라는 적당히 화려해서 좋다. **하나만 고르면 흑요석.**
