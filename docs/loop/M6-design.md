## 3. 엔진 쪽 추가 (A단계)

### 3.1 진행 알림

`QuickDiagnosis.RunAsync(…, IProgress<CheckResult>? progress = null)`: 검사 하나가 끝날 때마다(제한시간·오류 포함) 알린다. 판정·결론·반환값은 바꾸지 않는다.

### 3.2 데모 진단 검사기와 데모 설정 [1-5, 1-6]

**데모 설정** (`IAppWorld.Diagnostics.Settings`, 데모 세계만): 실제 기본값 대신 문서용 값.
- 외부 TCP 대상 = 시나리오의 외부 역할 대상 앞의 둘(`t1`, `t2`, 예: `198.51.100.10`, `203.0.113.20`).
- 빠른 진단 도메인 = `a.example`, `b.example` (슬롯 `t1`·`t2`, 같은 외부 대상에 대응).
- 네트워크 로그인 주소 = `http://portal.example/connecttest.txt`.
- 실시간 세계는 M4 기본값 그대로.

**응답 규칙** (호출된 그 순간에 정한다):
1. 그 순간의 시간축 회차 r = `DemoTimeBase.Scaled` 초. 데모 시간이 멈춰 있으면(`--demo-hold`) 모든 검사가 같은 r을 읽는다.
2. 우선순위: ① `diagnosis` 블록의 그 검사·슬롯 값 → ② 슬롯 규칙: TCP 주소·빠른 진단 도메인이 슬롯 `tN`이면 대응 외부 대상의 회차 r 결과(성공/응답 없음) → ③ 사이트 점검 도메인: `diagnosis.site[도메인]` → 문서용 도메인(`*.example`, `*.test`, `example.com|net|org`)은 성공 → 그 밖은 실패(`dns-HostNotFound`, HTTPS는 `no-address`).
3. 어댑터: `network`(유선·무선), 회차 r에 링크 다운이면 어댑터 내려감. 게이트웨이 Ping: 로컬 대상의 회차 r. 네트워크 로그인: 기본 정상. 링크: 회차 r 상태, 로그 지원, 최근 1,800회차 안 다운 여부.
4. `timeout`은 그 검사 제한시간보다 길게 기다려(취소에 응함) 조율자의 실제 제한시간 경로를 탄다. `delayMs`는 진행 장면용 지연.
5. 덮어쓰기에 없는 필드는 2·3 규칙을 따른다. 캡처·G3 장면은 **모든 검사를 덮어쓴 시나리오** 또는 **멈춘 시간축**만 쓴다 (재현성).

```json
"diagnosis": {
  "adapter": { "up": true, "ipv4": true, "apipa": false, "gateway": true, "dns": true },
  "gateway": "ok",
  "tcp": ["fail", "timeout"], "dns": ["ok", "ok"], "https": ["fail", "fail"],
  "portal": { "status": 302, "body": false },
  "link": { "now": "up", "log": "supported", "recentDown": false },
  "site": { "shop.example": { "dns": "ok", "https": "fail" } },
  "flushDns": "ok",
  "delayMs": { "https": 1500, "flushDns": 800 }
}
```

### 3.3 시스템 동작 (`ISystemActions`) [1-9]

```csharp
public interface ISystemActions
{
    Task<SystemActionResult> FlushDnsAsync(CancellationToken ct);   // 제한 10초
    SystemActionResult OpenSettings(SettingsPage page);             // Network, Wifi, Proxy
    SystemActionResult OpenFolder(string folder);
}
```

- **실제 구현 (Platform)**: 고정 명령만, 사용자 입력이 명령줄에 들어가지 않는다.
  - DNS 비우기: `%SystemRoot%\System32\ipconfig.exe /flushdns`, 셸 없이(`UseShellExecute=false`), 창 없이, 출력은 읽어 버리고 종료 코드만. 관리자 권한을 요청하지 않는다. 10초 넘으면 프로세스를 끝내고 `timeout`.
  - 설정 열기: 고정 주소 셋(`ms-settings:network-status`, `…network-wifi`, `…network-proxy`)만 셸로.
  - 폴더 열기: **허용 뿌리**(세계의 `RecordPaths` 둘 + 진단 기록 폴더)를 정규화(`Path.GetFullPath`, 끝 구분자)한 뒤, 열 폴더의 정규화 경로가 뿌리와 같거나 `뿌리 + 구분자`로 시작하고 실제로 존재할 때만 탐색기로 연다. 아니면 `not-allowed`·`missing`.
- **"기록 폴더 열기" 단추가 고르는 폴더** (명세서 3절): 측정 중이면 지금 측정의 조각 폴더(대체 위치일 수 있음), 아니면 기본 기록 위치(없으면 대체 위치, 둘 다 없으면 단추 비활성 + "아직 기록이 없습니다").
- **데모 구현 (Core)**: 실행하지 않고 호출을 기록(`Calls`), DNS 비우기 결과는 `diagnosis.flushDns`(기본 `ok`)·`delayMs.flushDns`. 시험·캡처·실측 시나리오는 실제 구현을 누르지 않는다 (실측 시험은 진단·사이트 점검만).

### 3.4 진단 수명 (`DiagnosisHost`, Core.Live) [1-1, 1-2, 1-7]

장면(`DiagnosisSnapshot`)과 `Changed` 알림, `MeasurementHost`와 같은 방식.

**작업 칸 하나**: 빠른 진단과 DNS 비우기 흐름은 한 칸(`Operation`: `None` / `Diagnosing` / `Flushing`)에서만 돈다. 사이트 점검은 별도 칸(`SiteRunning`).

| 요청 | 지금 `None` | `Diagnosing` | `Flushing` |
| --- | --- | --- | --- |
| 빠른 진단 시작 | 시작 | 무시 (`busy`) | 무시 (`busy`) |
| DNS 비우기 (확인 뒤) | 흐름 시작 | 흐름을 예약: 지금 진단이 끝나면 비우기 → 다시 진단 | 무시 (`busy`) |

- **DNS 비우기 흐름**은 하나의 작업이다: (진단 중이면 끝나기 기다림) → 비우기(최대 10초) → 다시 진단(흐름 안의 진단이라 `busy` 규칙을 타지 않음) → 결과에 메시지("DNS 캐시를 비웠습니다" / "비우지 못했습니다 (사유)") 붙여 게시. 흐름 동안 장면은 `Flushing`(단계: 기다림/비우는 중/다시 검사 중).
- **측정 Id**: 진단(흐름 안 다시 진단 포함)을 **시작하는 순간** `MeasurementHost.RunningId`를 한 번 읽어 결과와 함께 보관한다. 저장할 때 다시 읽지 않는다.
- **종료** (`ShutdownAsync`, 창 닫기에서 측정 종료 전에 부름): ① 새 요청 거부 ② 예약된 흐름 폐기 ③ 진행 중 작업 취소 ④ 최대 3초 기다림 ⑤ 종료가 시작된 뒤 끝난 결과는 **게시·저장·진행 알림·완료 알림 모두 하지 않는다** (취소로 생긴 `Error` 결과를 버림) ⑥ 장면 알림 구독 해제는 앱 틀이 화면을 떼기 전에. 사이트 점검도 같다.
- 실행 중 검사기 예외(조율자가 `Error`로 바꾼 것)는 결과의 일부로 보이고(검사 카드 "오류"), 앱 오류로 다루지 않는다.

### 3.5 진단 기록 저장과 읽기 (`DiagnosisStore`) [1-8]

- 위치: `사용자 폴더/diagnoses/`. 이름 `diagnosis-<시작 UTC>.json`, 있으면 `-2`, `-3` … (덮어쓰지 않음, `FileMode.CreateNew`로 경쟁 없이).
- 쓰기: 같은 폴더의 `.tmp` 파일에 쓰고 flush → 최종 이름으로 이동(바꾸기 없음). 실패하면 `.tmp`를 지우고 장면에 `SaveError`(코드). 결과 표시는 막지 않는다. 남은 `.tmp`는 읽을 때 무시.
- **이전 결과 선택**(비교 대상): 같은 앱 실행 안의 앞 결과가 있으면 그것. 없으면 기록 폴더에서 `StartedAt`이 가장 늦은 **읽을 수 있는**(`Ok`) 기록. 읽지 못한(`Unreadable`·`Unsupported`) 파일은 건너뛰고 그 수를 장면에 남긴다(비교 띠에 "읽지 못한 진단 기록 n개는 건너뛰었습니다"). 읽을 수 있는 것이 없으면 비교 없음.
- 홈 카드도 같은 "최근 결과"를 쓴다 (앱 시작 때 한 번 읽음).

### 3.6 화면용 모델 (`DiagnosisView`, `DiagnosisTexts`) [1-3, 1-4]

**결론 머리말** (단정하지 않음, 관측을 말함):

| 번호 | 머리말 | 무게 |
| --- | --- | --- |
| 1 | 어댑터 링크가 내려가 있음 | 문제 |
| 2 | 웹은 되지만 IPv4 직접 연결이 안 됨 | 주의 |
| 3 | 이름 해석(DNS)이 되지 않음 | 주의 |
| 4 | 로그인·프록시에 막혔을 수 있음 | 주의 |
| 5 | 이 PC의 연결에 문제가 있을 수 있음 | 문제 |
| 6 | 인터넷 쪽에서 응답이 없음 | 문제 |
| 7 | 웹(HTTPS) 연결 확인이 필요함 | 주의 |
| 8 | 최근 링크 끊김 기록이 있음 | 정보 |
| 9 | 인터넷은 되지만 예외가 관측됨 | 정보 |
| 10 | 일부만 성공 | 정보 |
| 11 | 기본 연결 정상 | 정상 |
| 12 | 진단 근거 부족 | 중립 |

무게는 상태 색(Bad/Warn/Accent/Ok/Muted) + 아이콘 + 머리말로 함께 (색만으로 구별하지 않음).

**관측 범위 줄** (결론 카드, 결론과 무관하게 늘): 핵심 검사(어댑터·TCP·DNS·HTTPS)와 게이트웨이마다 "외부 TCP 443: 대상 2개 중 1개 성공", "게이트웨이: 응답 없음 (Ping을 막는 장비일 수 있음)", "DNS: 확인하지 못한 대상이 있음" 같은 한 줄. 결론 문장이 일부 성공을 말하지 않는 조합(예: 결론 3에서 TCP 일부 성공)에서도 일부 성공이 카드에 보인다.

**검사 카드**: 이름, 판정 배지, 한 줄 설명(`Explain`), 펼치면 대상별 결과: "대상 1 · 198.51.100.10 · 성공 · 23 ms". **주소·도메인은 이 PC 화면의 펼친 상세에만** 보인다 (안내 "그 대상만의 문제일 수 있습니다"가 실행 가능하도록). 복사·진단 기록·리포트(M8)에는 넣지 않는다 (M4 C4 계약 그대로). 공개 캡처는 데모(문서용 값)만 쓴다.

**사유 코드 → 쉬운 말**: 엔진·검사기가 낼 수 있는 코드 전부 (`apipa`, `no-ipv4`, `no-gateway`, `no-route`, `adapter-down`, `interface-not-found`, `adapter-unmeasured`, `timeout`, `now-unknown`, `log-…`, `dns-…`, `no-address`, `tls-…`, `http-…`, 예외 형식 이름) — 모르는 코드는 "기타 사유 (코드)". G2가 코드 목록을 엔진 소스·검사기에서 모아 대조한다.

**비교 띠**: "지난 검사와 달라진 검사 n개" + "이전 → 지금", 없으면 "지난 검사와 같습니다", 처음이면 없음, 건너뛴 손상 기록 수.

## 4. 앱 (B단계)

### 4.1 진단 화면 배치

```
머리: "진단" + [빠른 진단 시작] (실행 중 "검사 중… 3/7", 비우기 흐름 중 "DNS 캐시 비우는 중")
┌ 결론 카드 (가장 크게) ──────────────────────────┐
│ 아이콘 · 머리말 · 문장                            │
│ 관측 범위 줄                                      │
│ 해볼 것 1. 2. 3.  [그 자리 도구 단추]            │
│ 다른 가능성 ▸ / 미측정 알림 / 비교 띠 / 메시지   │
│ [결과 복사]  마지막 검사 오후 1:20               │
└──────────────────────────────────────────────────┘
검사 카드 일곱 (넓으면 3열, 좁거나 150%면 2열~1열), Enter/Space로 펼침
┌ 사이트 점검 ─────────────┐ ┌ 보조 도구 ─────────────────────┐
│ [도메인] [점검]          │ │ DNS 캐시 비우기 (확인 후)       │
│ DNS · HTTPS 두 줄        │ │ 네트워크 / Wi‑Fi / 프록시 설정  │
└──────────────────────────┘ │ 기록 폴더 열기                 │
                             └────────────────────────────────┘
```

- 그 자리 도구: 결론 3 → [DNS 캐시 비우기], 결론 1·5 → [네트워크 설정 열기]. 결론 4는 단계만 (앱이 브라우저·외부 사이트를 열지 않음).
- 결과 복사: 클립보드에 쓰고 **되읽어 같을 때만** "결과를 복사했습니다", 아니면 "복사하지 못했습니다" (오류 알림) [1-10].
- DNS 비우기 확인 대화상자: "DNS 캐시를 비울까요? Windows가 기억한 이름 해석 결과를 지웁니다. 인터넷 연결이나 설정은 바뀌지 않습니다. 끝나면 빠른 진단을 다시 돌립니다." [비우기] [취소], 초점은 취소. 닫히면 초점은 누른 단추로 돌아간다.

### 4.3 홈 빠른 진단 카드

오른쪽 열(최근 측정 위, 좁으면 아래): 최근 결과의 머리말 + 언제 + [진단 열기]. 없으면 "빠른 진단으로 지금 연결을 검사해 보세요" + [진단 시작](진단 화면으로 가서 시작).

### 4.4 측정과의 관계

측정 중에도 진단할 수 있다. 진단 시작 순간의 측정 Id를 기록에 남긴다 (3.4). 진단 결과를 측정 화면·기록에 표시하는 것은 M7.

### 4.5 키보드와 화면 읽기

시작 Enter, 검사 카드 펼침 Enter/Space, 사이트 점검 Enter. 진행은 정중하게 한 번, 끝나면 머리말+문장. 대화상자 초점은 취소, 닫히면 원래 단추로.

### 4.6 부품

`DiagnosisParts`: `CheckCard`(펼침), `ConclusionCard`, `CompareStrip`. 기존 부품 위에, 새 색 없음.

## 5. 성능 [1-12]

빠른 진단은 최대 약 6초. 측정 화면 bench(12시간 기록)에 구간 셋을 더하고 같은 기준(전환 최대 50 ms, 33 ms 초과 2회)을 적용한다:
- `diag-enter`: 진단 화면 첫 진입 (시작 때 미리 배치할지를 이 값으로 정함, M5 이월 2와 함께).
- `diag-run`: 빠른 진단 진행 → 결과 표시 (데모 검사기 지연 포함).
- `diag-reenter`: 홈 ↔ 진단 6번.

## 6. M5 이월 (C단계에서 함께)

1. **종료 충돌 원인 (중요)** [1-14]: `AppDriver`의 모든 종료 경로(`Close`, `WaitExit`, 시작 실패, `Dispose`)에서 비정상 종료면 증거를 남기고 시험을 실패시킨다(지금은 일부만). 증거: 앱 기록, 그 프로세스의 Windows 응용 프로그램 로그 항목(Application Error·.NET Runtime, 읽기만), Windows 오류 보고가 만든 보고서 폴더(있으면 복사, 읽기만). 덤프 수집 설정(레지스트리 LocalDumps)은 시스템 설정을 바꾸므로 하지 않는다. 진단 중·비우기 흐름 중·테마 전환 중 창 닫기를 각 5회 반복하는 시험을 둔다. 다시 나면 원인을 찾아 고치고, 나지 않으면 반복 횟수와 함께 "재현 없음"을 G4에 보고한다.
2. **bench nav 여유 (사소)**: 첫 홈 이동 비용을 부분별로 재고, bench를 3회 돌려 최대값을 보고한다.
3. **관측 종류 전환 (사소)**: 상태 알약·알림을 지금 장면에서 계산한 값으로, 종류별 전환 추적. 시험: 외부 응답 없음 → 링크 끊김 전환에서 새 알림.
4. **시험 대기 조건 (중요, 시험)**: `RoundItemsArrive…` 시작 커서 0, `SessionLinkTests`의 `Rounds()` 게시까지.

## 7. 테스트 계획

### 7.1 G2 (CI에서도 돎)

- 데모 검사기: 슬롯 규칙(외부 대상 회차 결과), 덮어쓰기 우선순위, 사이트 도메인 규칙, 멈춘 시간축에서 모든 검사가 같은 회차, `timeout`이 실제 제한시간 경로(실행 상태 Timeout), 데모 설정에 실제 주소·도메인이 없음.
- 진행 알림: 일곱 검사가 한 번씩, 반환 결과와 같은 값.
- `DiagnosisHost`: 작업 칸 규칙 표 전부(진단 중 시작 무시, 진단 중 비우기 예약, 비우기 중 둘 다 무시), 비우기 흐름 순서(데모 동작 호출 순서·횟수), 측정 Id(진단 중 측정 중지·다음 측정 시작에도 시작 때 Id 유지), 종료(새 요청 거부, 예약 폐기, 종료 뒤 끝난 결과는 저장·게시 안 함), 사이트 점검 동시 실행·종료.
- `DiagnosisStore`: 같은 초 3회 이상 → `-2`, `-3`, 덮어쓰지 않음, `.tmp` 무시, 저장 실패 시 `.tmp` 없음, 최근 기록이 손상이면 그 앞 읽을 수 있는 기록 + 건너뛴 수.
- `DiagnosisView`·`DiagnosisTexts`: 결론 12종 머리말·무게, 관측 범위 줄(일부 성공·게이트웨이 무응답 단서), 사유 코드 표가 엔진·검사기 코드를 덮음, 비교 띠 문구.
- 복사 텍스트에 데모 시나리오 전부의 주소·도메인·대상 이름이 없음.
- 실제 시스템 동작(Platform): 폴더 허용 검사(뿌리 자체, 하위, 뿌리 이름이 앞부분만 같은 형제 `records-x` 거절, `..` 정규화, 없는 폴더) — 실행 없이 검사 함수만.

### 7.2 G3 데모 시나리오 (`M6FlowTests`, 로컬) [1-6, 1-10, 1-11]

장면마다 **기대 결론 번호와 검사 판정 일곱을 시험이 명시**하고, 화면과 비교한다. 추가로 앱이 저장한 기록을 다시 읽어 그 검사 판정으로 `Conclude`를 부른 결과 = 화면 결론.

1. 진단 처음 → 시작 → 진행 장면(지연) → 결과 (결론 11). 저장 기록 = 화면.
2. 결론별 장면 8종(11, 3, 6, 1, 4, 10, 12, 2): 기대 결론·판정·관측 범위 줄.
3. 다시 검사(시나리오가 달라지는 멈춤 해제 장면) → 비교 띠 = `Compare`.
4. 결과 복사 → 시험이 **실제 클립보드를 읽어** = `CopyText` (시험 전 클립보드 글을 보관하고 끝나면 되돌림).
5. 사이트 점검: 잘못된 입력 셋 → 칸 오류·실행 안 함. 정상(`shop.example` 성공), 실패, 시간 초과 장면.
6. DNS 비우기: 결론 3 → 단추 → 대화상자 → 취소(동작 0회, 초점 복귀) → 확인(1회) → 다시 진단 → 메시지. 진단 중 비우기 → 예약 안내 → 끝난 뒤 비우기·다시 진단. 비우기 실패·시간 초과 메시지.
7. 측정 중 진단 → 진단 중 측정 중지 → 기록의 `measurementId` = 진단 시작 때 측정 Id. 홈 카드 → 진단 화면.
8. 기록 폴더 열기: 측정 중이면 측정 조각 폴더, 아니면 기록 뿌리 (데모 동작 호출 인수).
9. 키보드만으로: 진단 화면 → 시작 → 검사 카드 펼침 → 사이트 점검 입력·Enter → DNS 대화상자 취소·확인과 초점 복귀.
10. 종료 반복 (6.1): 진단 중·비우기 흐름 중 창 닫기 각 5회, 종료 코드 0과 저장 파일 없음/있음 규칙.

## 9. 대안

- 진단을 모달 창으로: 7.5 "창 하나"에 어긋나 버림.
- 브라우저로 로그인 페이지 열기(결론 4): 외부 사이트를 열지 않는 규칙에 어긋나 단계 안내만.
- DNS 비우기를 Win32 `DnsFlushResolverCache`로: 문서화되지 않은 API라 고정 명령.
- 주소를 화면에서도 전부 감추기(1판): 안내를 실행할 수 없어 펼친 상세에만 보이기로 바꿈 [1-4].
- 클립보드 대신 진단 값 비교(1판): 실제 쓰기 실패를 못 잡아 되읽기·실제 클립보드 검사로 [1-10].
